# Naia ADK

**AI कोडिंग एजेंटों के काम करने के लिए पहले से तैयार कार्यक्षेत्र का ढांचा।**

जब आप Claude Code या Codex जैसे AI कोडिंग टूल इस्तेमाल करते हैं, तो हर टूल अपनी
नियम-फाइलें अलग जगह रखता है, और «क्या यह दस्तावेज़ प्रकाशित हो सकता है?» या
«स्किल कहां जाएं?» जैसे सवालों के जवाब जुगाड़ से मिलते हैं। Naia ADK यह ढांचा
पहले से तय कर देता है। जैसे नए लैपटॉप पर पहले विकास वातावरण तैयार करते हैं, वैसे
ही यह AI एजेंट को शुरू करने के लिए साफ-सुथरा डेस्क सौंपता है। साथ में एक
डैशबोर्ड भी है जिससे कार्यक्षेत्र की स्थिति एक नज़र में दिखती है।

## 5 मिनट में शुरू करें

आपको **Node 22+** और **pnpm 9+** चाहिए।

```bash
pnpm install    # install workspace dependencies
pnpm dev        # run the API server (:3141) and dashboard (:3142) together
```

डैशबोर्ड देखने के लिए ब्राउज़र में `http://localhost:3142` खोलें। तुरंत तीन चीज़ें
दिखती हैं:

- **Workspace** — प्रोजेक्ट और सबमॉड्यूल, फाइल वृक्ष, और हर आइटम का प्रकटीकरण
  स्तर।
- **Skills catalog** — इस कार्यक्षेत्र में पंजीकृत स्किलों की सूची और उनकी
  सामग्री।
- **Settings / monitoring** — सर्वर विन्यास, क्लाइंट स्थिति, डेटा निर्देशिकाएं।

डैशबोर्ड API सर्वर (पोर्ट 3141) को केवल दस्तावेज़ दृश्य के `/api/portal` अनुरोध
भेजता है। दोनों में से केवल एक चलाने के लिए `pnpm dev:server` (→ 3141) या
`pnpm dev:dashboard` (→ 3142) इस्तेमाल करें। प्रारंभ स्क्रिप्ट `./start.sh`
(Linux/macOS) और `start.bat` (Windows) दोनों `pnpm dev` चलाते हैं। सर्वर CLI
`--port`, `--host` और `--root` स्वीकार करता है; उदाहरण के लिए इसे
`pnpm serve -- --root /path/to/workspace` से किसी अन्य कार्यक्षेत्र की ओर इंगित
करें।

## अंदर क्या है

### कार्यक्षेत्र का ढांचा

यह AI एजेंट को हर चीज़ के लिए तय स्थानों वाली निर्देशिका संरचना देता है, ताकि वह
तुरंत काम शुरू कर सके। AI-संदर्भ `.agents/` में रहता है (अंग्रेज़ी, JSON/YAML)।
मानव-पठनीय मार्गदर्शिकाएं `.users/context/` (कोरियाई) और `.users/context/en/`
(अंग्रेज़ी) में रहती हैं। यह दर्पण आंशिक है, पूर्ण प्रति नहीं — इसमें केवल वही
दस्तावेज़ हैं जो मानव को पढ़ने चाहिए (उदाहरण के लिए स्किल मानक रूप से
`.agents/skills/` में हैं, और केवल कुछ `.users/skills/` में प्रतिबिंबित हैं)।
स्किल, डेटा और प्रोजेक्ट सभी के निर्धारित स्थान हैं, इसलिए कार्यक्षेत्र एक जैसा
दिखता है चाहे जो भी टूल इसे खोले।

### डैशबोर्ड और API

Next.js डैशबोर्ड कार्यक्षेत्र का दृश्य प्रबंधन करता है, जिसके पीछे Fastify API
सर्वर है। शीर्ष नेविगेशन के **Docs** (`/docs`) और **Work** टैब साझा कंपनी
दस्तावेज़ और सहयोग बोर्ड एक ही जगह दिखाते हैं, और
`pnpm adk:setup -- --company <repo-url>` कंपनी दस्तावेज़ और प्रोजेक्ट रिपो एक ही
चरण में स्थापित कर देता है। सेटअप और उपयोग विवरण के लिए
[ऑनबोर्डिंग मार्गदर्शिका](docs/guides/onboarding.en.md)
([한국어](docs/guides/onboarding.ko.md)) देखें।
आर्किटेक्चर, अनुबंध और कार्यान्वयन साक्ष्य दर्ज करने के लिए
[विकास दस्तावेज़ लेखन मार्गदर्शिका](docs/guides/dev-docs-writing.en.md) देखें।
API कार्यक्षेत्र मेटाडेटा (`/api/workspace`), स्किल सूची (`/api/skills`),
कंपनी दस्तावेज़ पोर्टल (`/api/portal`), और फाइल-परिवर्तन घटनाएं भेजने वाला
WebSocket (`/api/ws`) उजागर करता है। इस API की बदौलत डैशबोर्ड के अलावा अन्य
प्रोग्राम भी कार्यक्षेत्र तक पहुंच सकते हैं।

### स्किल प्रणाली

दोहराए जाने वाले कार्य पुन: प्रयोज्य स्किलों में समेटे जाते हैं। हर स्किल केवल एक
`SKILL.md` से परिभाषित होता है, और API सर्वर सूची बनाने के लिए `skills/` स्कैन
करता है। यदि एक भी स्किल प्रारूप तोड़ता है, तो पूरी सूची त्रुटि देती है
(विफल-बंद): टूटे स्किल को चुपचाप छोड़कर बाकी परोसने के बजाय ऑपरेटर को तुरंत ठीक
करने के लिए बाध्य किया जाता है। अधूरी सूची गलती से न चली जाए, इसलिए यह सोचकर
लिया गया निर्णय है।

### आज स्किल वृक्ष में क्या है

स्किल चार समूहों में बंटे हैं। ताकि सत्र को यह जानने के लिए हर `SKILL.md` दोबारा
न पढ़ना पड़े कि क्या मौजूद है, `.agents/context/skills-index.yaml` प्रति स्किल एक
पंक्ति रखता है जो बताती है कि वह क्या करता है और कब उसका उपयोग करें। नीचे दी सूची
उसी सूचकांक की विषय-सूची है।

**दस्तावेज़ और बाहरी कार्य** — वे चीज़ें जो कोई व्यक्ति पढ़ेगा।
`doc-coauthoring` (विनिर्देश और डिज़ाइन दस्तावेज़), `proposal-writing`,
`read-doc`, `translate-doc`, `press-release`, `weekly-report`,
`document-generation` (ब्रांडेड PDF और डिजिटल हस्ताक्षर), `copyright-reg`
(कॉपीराइट पंजीकरण), `patent-draft` और `patent-pipeline` (पेटेंट विनिर्देश),
`youtube-upload` (वीडियो और उपशीर्षक)।

**कार्यक्षेत्र चलाना** — वे हाथ जो रिपो को छूते हैं।
`project-create`, `project-migration`, `merge-worktree`, `migrate-ctx`,
`session-resume`, `sync-upstream` (अपस्ट्रीम समन्वय), `manage-skills`, और
एन्क्रिप्टेड गुप्त-तिजोरी के लिए `secret-vault`।

**सत्यापन द्वार** — वे स्थान जो दावे के बजाय साक्ष्य मांगते हैं।
`verify-implementation`, `verify-contract-conformance`, `verify-request-contract`,
`verify-product-preservation`, `verify-benchmark-contract`, `verify-review-gate`,
`verify-build` (क्या सच में बनता है), `verify-conflict-markers` (क्या विरोध
चिह्न बचे हैं), `verify-i18n` और `verify-hardcoded-strings` (क्या स्ट्रिंग सही
जगह हैं), `webapp-testing`, और प्रतिकूल समीक्षा के लिए `review-pass`।

**संचालन और प्रयोग** — वह कार्य जो बाहर पहुंचता है या मॉडल छूता है।
Discord गेटवे के लिए `manage-discord-sessions`, `channel-management`,
`service-management` (अपटाइम, लागत, घटनाएं), `web-monitoring`, `email`, `sms`,
`upstream-pr-review` (OSS अनुरक्षक तक जाने वाली हर चीज़ से पहले एक जांच),
`payroll`, और पात्र LoRA प्रशिक्षण के लिए `finetune-persona`।

`.agents/skills/SKILL_TEMPLATE.md` से नया स्किल शुरू करें, और उसके बनते ही उसकी
पंक्ति सूचकांक में जोड़ें। जब सूचकांक वृक्ष से हट जाए, तो अगला सत्र पहले से मौजूद
स्किल को फिर से बनाता है।

### नियम और न्यूनतम अनुशासन

अकेले इस्तेमाल वाले कार्यक्षेत्र को भी कुछ न्यूनतम नियम चाहिए, जैसे ही AI और
स्वचालन उसे छूते हैं। Naia ADK `read`, `write`, `execute` और `publish` को अलग-अलग
मामलों के रूप में बांटता है, और हर दस्तावेज़ से प्रकटीकरण स्तर जोड़ता है। कठिनाई
से पलटे जाने वाले कार्य — उत्पादन परिवर्तन, गुप्त-प्रबंधन, सार्वजनिक दावे —
साधारण स्थानीय संपादनों से अलग कर अनुमोदन द्वारों से भेजे जाते हैं।

प्रकटीकरण के चार स्तर हैं। `public` सार्वजनिक साइट या ओपन-सोर्स रिपो पर ज्यों का
त्यों सुरक्षित है; `controlled` समीक्षा के बाद बाहर साझा हो सकता है; `internal`
कार्यक्षेत्र के अंदर रहता है; `confidential` अनुबंध, क्रेडेंशियल और व्यक्तिगत
डेटा जैसी संवेदनशील सामग्री ढकता है। क्रेडेंशियल आमतौर पर git के बाहर रहते हैं,
लेकिन स्तर के हिसाब से फिर भी `confidential` हैं।

> **सत्र-अनुबंध द्वार चिह्न-मुक्त checkout में सक्रिय है।** अबद्ध सत्र नीति-अनुमत
> सामान्य स्थानीय कार्य कर सकता है जैसे निरीक्षण, `npm test`, बिल्ड, `mkdir`, और
> सामान्य गैर-विनाशकारी Git stage/commit। अनुशासन और होस्ट-नीति फाइलें, साझा
> प्रवेश-बिंदु, सत्र अनुबंध और रजिस्ट्री प्राधिकार, विलोपन, विनाशकारी या दूरस्थ
> आदेश, बाहरी प्रभाव, और उत्पादन परिवर्तन अभी भी अनुबंध मांगते हैं। यह रिपो हुक
> का अनुशासन जांच है; यह ऑपरेटिंग-सिस्टम सैंडबॉक्स नहीं है और हुक के बाहर चलाए
> आदेशों की गारंटी नहीं देता। नीति के लिए `.agents/context/agents-rules.json` और
> `.agents/context/harness.yaml` देखें। प्रोजेक्ट मूल या किसी पूर्वज पर
> `.codex/no-harness`, `.claude/no-harness`, या `.pi/no-harness` चिह्न वंशज
> checkout को विरासत में मिलता है। यह उम्मीदवार सत्र-अनुबंध हुक को Codex और
> Claude से जोड़ता है; यह Pi सत्र-अनुबंध एडाप्टर का दावा नहीं करता।

### गुप्त बातें कहां रहती हैं

API कुंजियां और प्रमाणपत्र git में commit नहीं हो सकते। लेकिन उन्हें केवल हर
लैपटॉप पर रखने का मतलब है कि मशीन बदलते ही वे गायब हो जाते हैं, और कोई नहीं कह
सकता किसके पास क्या है। Naia ADK इस उलझन को **ठीक एक फाइल** commit करके सुलझाता
है: गुप्त बातों का फ़ोल्डर, संग्रहीत और एन्क्रिप्टेड। डिक्रिप्ट की गई सामग्री git
कभी नहीं देखता।

ठोस रूप में, `key/` फ़ोल्डर tar किया जाता है और
[age](https://github.com/FiloSottile/age) से एकल `key.age` में एन्क्रिप्ट होता है।
`key/` `.gitignore` में है, इसलिए गलती से commit नहीं हो सकता। commit में जाने
वाली एकमात्र चीज़ `key.age` है।

पासफ़्रेज़ व्यक्ति टाइप करता है। AI न तो इसे पाता है न किसी की ओर से टाइप करता
है। इसलिए तिजोरी खोलना और सील करना उपयोगकर्ता के अपने टर्मिनल में होता है, जबकि
जांच और बैकअप — जिन्हें पासफ़्रेज़ नहीं चाहिए — सौंपे जा सकते हैं। वह सीमा स्किल
के अंदर आदेश-दर-आदेश खींची जाती है।

```bash
bash .agents/skills/secret-vault/scripts/vault.sh init     # create a vault in a new repo
bash .agents/skills/secret-vault/scripts/vault.sh unlock   # open it (passphrase)
bash .agents/skills/secret-vault/scripts/vault.sh lock     # seal it again (passphrase)
bash .agents/skills/secret-vault/scripts/vault.sh status   # is the backup current?
bash .agents/skills/secret-vault/scripts/vault.sh sync     # commit key.age and push
```

`status` इसलिए है क्योंकि गलतियों का आकार तय है। आप कुंजी जोड़ते हैं और सील करना
भूल जाते हैं, या सील करते हैं और धक्का देना भूल जाते हैं, या अस्थायी फाइल पीछे
छूट जाती है। `status` तीनों को एक साथ खोजता है। जब कोई पूछे कि कुंजियों का बैकअप
है या नहीं, तो याददाश्त से नहीं, इस आदेश से उत्तर दें।

`lock` नया सिफरटेक्स्ट लिखता है, **इसे जांचने के लिए फिर से डिक्रिप्ट करता है**,
और तभी पुरानी फाइल बदलता है — ताकि अधूरी सील कभी टूटी तिजोरी न छोड़े।

इस पैटर्न का मानक उपभोक्ता `data-private` जैसा निजी रिपो है, लेकिन `key.age` और
git-उपेक्षित `key/` वाला कोई भी रिपो इसे इस्तेमाल कर सकता है। किसी भी पक्ष का
नाम बदलने के लिए `VAULT` और `PLAIN_DIR` ओवरराइड करें।

### LLM एडाप्टर (naia-anyllm)

उन सुविधाओं के लिए जिन्हें LLM तक पहुंचना है, `naia-anyllm` एडाप्टर अंतर्निहित
है। यह [any-llm](https://github.com/nextain/any-llm) गेटवे के माध्यम से, या सीधे
OpenAI, Anthropic और Google जैसे प्रदाताओं से जुड़ता है। डिफ़ॉल्ट Naia खाता है:
[naia.nextain.io](https://naia.nextain.io) पर जारी कुंजी `NAIA_KEY` वातावरण चर में
रखें और आप तुरंत अपने खाता क्रेडिट इस्तेमाल कर सकते हैं। बिना कुंजी, यह किसी भी
भुगतान कॉल से पहले त्रुटि देता है। प्रदाता या मॉडल बदलने के लिए
[`.agents/context/llm-config.yaml.example`](.agents/context/llm-config.yaml.example)
प्रतिलिपि करें, और API कुंजियां वातावरण चर या ऑपरेटिंग सिस्टम कीस्टोर में रखें,
कॉन्फ़िग फाइल में कभी नहीं। `naia-settings/llm.json` केवल
`apiKeyRef: "NAIA_KEY"` दर्ज करता है, कुंजी मान कभी नहीं। यदि व्यक्तिगत फ़ोर्क को
दीर्घकालिक बैकअप चाहिए, तो `data-private/key/` में age-एन्क्रिप्टेड तिजोरी
इस्तेमाल करें ([`.env.example`](.env.example) देखें)।

समर्थित मॉडल और वर्तमान मूल्य सूचीबद्ध करने के लिए, और लंबी PDF अनुवाद के लिए,
`translate-doc` स्किल इस्तेमाल करें। मॉडल और मूल्य खोज बिना कुंजी काम करती है;
अनुवाद पहले अनुमानित लागत दिखाता है और जहां रुका था वहां से फिर शुरू हो सकता है।

## इसे इस तरह क्यों बनाया गया

### प्रारूप ही अनुबंध है

Naia ADK का हृदय कोई विशेष टूल नहीं बल्कि एक **प्रारूप** है। निर्देशिका विन्यास
(`.agents/`, `.users/`, `skills/`, `data-*/`) और फाइल स्कीमा
(`agents-rules.json`, `SKILL.md`) एक तय समझौता हैं, और जो भी टूल उस समझौते को पढ़
सकता है वही कार्यक्षेत्र उपयोग कर सकता है। Claude Code, Codex, opencode,
naia-agent, agy और muse एक-दूसरे का कोड डाले बिना एक ही कार्यक्षेत्र पढ़ते हैं।
इसलिए आप टूल बदल सकते हैं या कई मिला सकते हैं, और कार्यक्षेत्र चलता रहता है।

नियम प्रवर्तन भी टूल-अज्ञेय है। होस्ट-तटस्थ कोर (`.agents/hooks/core/`) और
नीतियां (`.agents/hooks/policies/`) Claude Code हुक और pi एक्सटेंशन दोनों को एक
ही नियमों से चलाती हैं।

### टीम बनने से पहले व्यक्तिगत आधार

Naia ADK पूरी तरह एकल-उपयोगकर्ता है, व्यक्तिगत उपयोग के लिए। कंपनी संगठन-चार्ट,
टेनेंट नियम, और प्रत्यायोजित अनुमोदन श्रृंखलाएं ऊपरी परत की हैं। यह आपको देता है
कार्यक्षेत्र के टीम या कंपनी पैमाने पर बढ़ने से पहले संदर्भ अनुशासन लिखने की एक
जगह।

टीम सहयोग और साझा ज्ञान के लिए, आप
[Naia Business ADK](https://nextain.io/adk) द्वारा दर्शाया गया वैकल्पिक संगठन-वंश
चुन सकते हैं। यह संपत्ति, प्रक्रिया और अनुमति अनुशासन, टीम स्वामित्व, और
प्रत्यायोजित अनुमोदन जोड़ता है।

### फ़ोर्क वंशावली

Naia ADK आपके अपने कार्यक्षेत्र में फ़ोर्क होने के लिए बना है। व्यक्ति `naia-adk`
सीधे फ़ोर्क कर सकते हैं। संगठन कंपनी और सदस्य कार्यक्षेत्रों के लिए
`naia-business-adk` जैसी अलग संगठन-वंशावली चुन सकता है। किसी भी उपयोगकर्ता के
लिए एकल तय श्रृंखला आवश्यक नहीं है।

```
naia-adk                  ← public personal base (Apache 2.0)
  └── {user}-adk          ← direct personal fork

naia-business-adk         ← optional organization lineage
  └── {org}-adk            ← org fork: company data + business submodules
        └── {member}-adk    ← member workspace derived from the organization
```

Nextain की आंतरिक वंशावली एक अलग परिचालन उदाहरण है। सार्वजनिक उपयोगकर्ता सीधा
व्यक्तिगत फ़ोर्क रख सकता है और खाता नाम से उसे `{user}-adk` नाम दे सकता है।

यदि आपको प्रोजेक्ट/टीम आधार चाहिए, तो आप
[naia-pj-adk](https://github.com/nextain/naia-pj-adk) अलग आधार के रूप में चुन
सकते हैं। PJ बहु-प्रोजेक्ट संदर्भ-विचलन, कॉल लागत, और Discord संचालन सीमाओं के
लिए एडाप्टर आधार है। व्यक्तिगत-फ़ोर्क अनुकूलन और टीम भूमिका/कार्य-घंटे नियम अलग
मामले हैं। उस कार्य को व्यवस्थित और अनुरेखणीय बनाने में मदद करना इस संरचना का
डिज़ाइन लक्ष्य है, लागत बचत या कम कार्य समय की मापी गारंटी नहीं। PJ आधार
व्यक्तिगत फ़ोर्क का मूल रिपो नहीं है। संगठनात्मक सहयोग के लिए `naia-business-adk`
वैकल्पिक है।

## संरचना

रिपो रनटाइम कोड (`packages/`), नियम और संदर्भ (`.agents/`, `.users/`), स्किल
(`skills/`, `.agents/skills/`), और वे डेटा निर्देशिकाएं जिनहें हर फ़ोर्क भरता है,
में बंटा है।

| Directory | Purpose |
|-----------|---------|
| `.agents/` | AI-संदर्भ (अंग्रेज़ी, JSON/YAML) — नियमों के लिए सत्य का एकल स्रोत |
| `.users/context/` | मानव-पठनीय मार्गदर्शिकाएं (कोरियाई, Markdown) |
| `.users/context/en/` | अंग्रेज़ी मानव-पठनीय दर्पण (Markdown) |
| `.claude/` | Claude Code विन्यास, हुक, स्किल सिमलिंक |
| `skills/` | परिचालन/रनटाइम स्किल (डैशबोर्ड API द्वारा परोसे गए) |
| `scripts/` | उपयोगिता स्क्रिप्ट |
| `templates/` | दस्तावेज़ टेम्पलेट |
| `docs/` | आर्किटेक्चर दस्तावेज़, डिज़ाइन विनिर्देश |
| `packages/` | रनटाइम पैकेज (pnpm कार्यक्षेत्र) |
| `config/` | उदाहरण कार्यकर्ता-स्तर प्रोफ़ाइल और तैनाती विन्यास |

### रनटाइम पैकेज (packages/, कुल 12)

तीन वास्तव में चलने वाले प्रोग्राम हैं; बाकी पतले पैकेज हैं जो प्रारूप और
विनिर्देश परिभाषित करते हैं।

- `core` — कार्यक्षेत्र और स्किल पार्स करने वाला इंजन।
- `server` — Fastify REST/WebSocket API।
- `dashboard` — Next.js डैशबोर्ड UI।
- `skill-spec` — टूल-अज्ञेय स्किल प्रारूप अनुबंध (`SkillDescriptor`,
  `SkillLoader`)।
- `skills-builtin` — सामान्य स्किल सूची।
- `openclaw-compat` — OpenClaw स्किलों को naia प्रारूप में लाने वाला टूल।
- `persona` — सिस्टम-प्रॉम्प्ट परंपरा विनिर्देश।
- `process` — कार्यप्रवाह पैटर्न विनिर्देश (समीक्षा → निर्णय → निष्पादन,
  समस्या-चालित विकास, आदि)।
- `naia-anyllm` — any-llm गेटवे / प्रत्यक्ष-प्रदाता LLM एडाप्टर।
- `artifacts-spec` — अनुमति (RBAC) और विकास जीवनचक्र (SDLC) शिल्पकृतियों के लिए
  मानक स्कीमा। यह 15 शिल्पकृति प्रकारों को JSON Schema के रूप में परिभाषित करता
  है और प्रत्येक के लिए बताता है कि इंस्टेंस git-ट्रैक्ड है या सत्र-सीमित।
- `ax-messenger` — Matrix संदेशवाहक रिले/प्रशासन पैकेज (AI रिले, लेजर और
  `matrix-js-sdk` पर प्रदाता)।
- `benchmark-contract` — `naia-adk` और `naia-agent` द्वारा साझा स्थायी बेंचमार्क
  और अनुशासन साक्ष्य अनुबंध।

### कार्यकर्ता स्तर और समीक्षक ओवरराइड

भूमिकाएं और मॉडल अलग-अलग विन्यस्त हैं — कोई मॉडल संस्करण आर्किटेक्चर में नहीं
पकाया गया।

- `config/tier-profile.example.json` (`tier-profile/v1`) एक मॉडल-अज्ञेय 4-स्तरीय
  कार्यकर्ता प्रोफ़ाइल है। स्तर *भूमिकाएं* बताते हैं (हल्की जांच, डिज़ाइन और
  कार्यान्वयन, भूमिका सत्र, स्वतंत्र समीक्षा); हर स्तर के उम्मीदवार CLI और मॉडल
  अलग-अलग बांधते हैं, इसलिए मॉडल बदलने से भूमिका संरचना कभी नहीं बदलती।
- अनुमोदन-द्वार समीक्षक ओवरराइड इंस्टेंस के `.claude/deploy/config.json` में
  `review_models` के रूप में रहते हैं (समीक्षक id → सटीक मॉडल, न्यूनतम प्रयास,
  रनर)। वे केवल `CFG-` अनुमोदन के बाद लागू होते हैं; अनुमोदित विन्यास के बिना कोड
  डिफ़ॉल्ट लागू होते हैं। रनर में `agy`, `muse`, `codex` और `claude` शामिल हैं।
  [अनुमोदन योजना द्वार मार्गदर्शिका](docs/guides/approval-plan-gate.en.md) देखें।
- `naia-settings/review.json` क्रॉस-रिपो समीक्षा पैनल और मॉडल स्तर नीति रखता है
  जिसे `review-pass` स्किल और `naia-agent` उपयोग करते हैं।

### डेटा निर्देशिकाएं (gitignored, प्रति फ़ोर्क भरी गई)

ये चार कभी commit नहीं होतीं। जो भी रिपो फ़ोर्क करता है वह अपना डेटा भरता है।

| Directory | Scope | Content |
|-----------|-------|---------|
| `data-company/` | Company | कंपनी-व्यापी दस्तावेज़, साझा संसाधन |
| `data-teams/` | Team | टीम दस्तावेज़ (रणनीति, लेखा, आदि) |
| `data-private/` | Personal | व्यक्तिगत डेटा, env फाइलें, निजी दस्तावेज़ |
| `projects/` | Personal | प्रोजेक्ट रिपो (सबमॉड्यूल) |

### दो स्किल वृक्ष

स्किल दो जगह रहते हैं, जिन्हें अलग पक्ष उपयोग करते हैं।

- `.agents/skills/` — AI-सहायता और कार्यप्रवाह स्किल। Claude Code इन्हें
  `.claude/skills/` सिमलिंक से इस्तेमाल करता है। इसमें समीक्षा (`review-pass`),
  सत्यापन (`verify-implementation`), वर्कट्री विलय (`merge-worktree`),
  दस्तावेज़ निष्कर्षण (`read-doc`), पेटेंट/कॉपीराइट/पेरोल जैसे व्यावसायिक स्किल,
  और अन्य जैसे `finetune-persona`, `secret-vault` और `youtube-upload` शामिल हैं।
- `skills/` — परिचालन/रनटाइम स्किल। API सर्वर `skills/**/SKILL.md` स्कैन करता है
  और डैशबोर्ड को परोसता है। इनमें ईमेल/SMS/सूचना भेजना, चैनल प्रबंधन, सेवा और
  वेब निगरानी, और दस्तावेज़ निर्माण शामिल हैं; `skills/business/` में
  `press-release` जैसे संगठन स्किल हैं।

सबसे सटीक सूची डैशबोर्ड में स्किल सूची है। पाठ तालिका
[स्किल सूचकांक](.agents/context/skills-index.yaml) में है।

## शुरू करना

### व्यक्तिगत

1. `naia-adk` को अपने खाते में फ़ोर्क करें (हो सके तो निजी)।
2. क्लोन करें: `git clone https://github.com/YOUR-USER/your-adk.git && cd your-adk`
3. अपस्ट्रीम जोड़ें: `git remote add upstream https://github.com/nextain/naia-adk.git`
4. डेटा निर्देशिकाएं बनाएं: `mkdir -p data-private projects`
5. प्रोजेक्ट जोड़ें, `.agents/` विन्यस्त करें, और काम शुरू करें।
6. यदि Naia खाता संसाधन इस्तेमाल करते हैं, तो `NAIA_KEY` वातावरण चर के रूप में
   सेट करें।
7. समय-समय पर समन्वय करें: `git fetch upstream && git merge upstream/main`

### कंपनी

1. `naia-business-adk` पहुंच के लिए [संपर्क करें](https://nextain.io/contact)।
2. `naia-business-adk` को संगठन खाते में निजी फ़ोर्क करें, फिर क्लोन करें।
3. अपस्ट्रीम जोड़ें: `git remote add upstream https://github.com/nextain/naia-business-adk.git`
4. कंपनी डेटा और प्रोजेक्ट सबमॉड्यूल भरें: `mkdir -p data-company projects`,
   `git submodule add <repo> projects/<name>`
5. हर सदस्य संगठन ADK को फिर से व्यक्तिगत कार्यक्षेत्र के रूप में फ़ोर्क करता है।

### Naia Shell एकीकरण (वैकल्पिक)

यदि आप [Naia Shell](https://github.com/nextain/naia-shell) डेस्कटॉप व वेब ऐप
इस्तेमाल करते हैं, तो उसके कार्यक्षेत्र पथ को अपनी ADK निर्देशिका की ओर इंगित
करें। स्किल और डेटा API पर परोसे जाते हैं।
