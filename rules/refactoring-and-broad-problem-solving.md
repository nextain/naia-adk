# 리팩토링 원칙·광범위 문제해결 위임 및 코드 복잡도 게이트 (`USR-012`)

범위: 공통 (`naia-adk` v0.2.0 표준 규칙)

---

## 1. 문제 배경 (안티패턴)

지휘(오케스트레이션) 세션이 하위 작업자(서브에이전트·원샷 실행기)에게 일을 맡길 때 **"이 파일의 몇 줄만 최소 수정하라"**고 파일·줄 범위를 좁게 제한하면 다음과 같은 구조적 부패가 발생한다.

1. **거대 단일 파일(God File) 누적**: 작업자가 새 파일을 만들거나 책임을 분리할 권한이 없다고 판단해 기존 파일에 조건문·분기만 계속 덧붙인다(예: 단일 감시 스크립트가 130KB~190KB 이상으로 비대화).
2. **근본 원인 회피(Symptom Patching)**: 모듈 경계나 상태 구조의 결함을 고치는 대신 눈앞의 실패 케이스 하나만 우회하는 임시 분기를 넣는다.
3. **문맥 예산 폭발 및 리뷰 품질 저하**: 파일 하나가 수천 줄이 되면 읽기와 검수 때마다 토큰 비용이 급증하고 부작용 추적이 불가능해진다.

---

## 2. 광범위 문제해결 위임 원칙 (Broad Problem-Solving Delegation)

하위 에이전트에게 작업을 위임할 때는 파일·함수·줄 번호를 좁게 묶지 않고 다음 **5대 요소**를 명확히 전달한다.

| 위임 요소 | 포함해야 할 내용 | 금지 패턴 |
|---|---|---|
| **1. 상위 미션 블록 (Mission Block)** | 사용자가 달성하려는 원래 목적과 제품/아키텍처 맥락 원문 | 목적을 생략한 채 단편적 코드 수정만 지시 |
| **2. 해결할 문제와 근본 원인 (Problem & Root Cause)** | 관측된 현상, 재현 조건, 확인된(또는 규명해야 할) 근본 원인 | 증상만 가리는 임시 우회(workaround) 지시 |
| **3. 목표와 수용 조건 (Goal & Acceptance Criteria)** | 완료 후 만족해야 할 동작 불변식, 스펙 체인 연결(`PC/SP/UC/RQ/FE`), 성능·안전 기준 | 모호한 "적당히 수정" 또는 검증 불가능한 지시 |
| **4. 리팩토링·모듈 분리 권한 (Modularity Authority)** | 단일 책임 원칙(SRP)과 코드 단순성 유지를 위해 거대 파일을 역할별 하위 모듈로 분리·추출할 명시적 권한 | "기존 파일 하나만 건드리고 새 파일을 만들지 말라"는 과도한 파일 수 제한 |
| **5. 결정론적 검증 방법 (Verification)** | 단위·통합·E2E 시험 명령과 복잡도 게이트(`measure-complexity.mjs` / `review-preflight.mjs`) 통과 조건 | 실행 명령·종료 코드 없는 구두 완료 보고 |

> **최소 변경 원칙의 정확한 구분**:
> - **제품 범위(What)**: 사용자가 승인하지 않은 새 기능·외부 동작은 임의로 추가하지 않는다(`no_autonomous_development`).
> - **코드 구조(How)**: 승인된 문제를 해결할 때 코드 단순성과 유지보수성을 지키기 위한 **책임 분리·함수/모듈 추출·중복 제거 리팩토링은 필수 의무**다.

---

## 3. 결정론적 코드 복잡도 게이트 (`USR-012`)

모든 코드 변경은 개발 완료 전과 독립 리뷰 진입 전(`review-preflight.mjs` → `measure-complexity.mjs`)에 아래 정량 임계치를 통과해야 한다.

### 3.1 정량 임계치 표

| 등급 | 줄 수 기준 (`lines`) | 바이트 기준 (`bytes`) | 대형 파일 증분 (`growthLines`) | 판정 및 조치 |
|---|---:|---:|---:|---|
| **정상 (`OK`)** | `< 500` 줄 | `< 80,000` B | — | 통과 |
| **경고 (`WARNING`)** | `>= 500` 줄 | `>= 80,000` B | — | 경고 기록 — 새 기능 추가 전 책임 분리 권고 |
| **리팩토링 필수 (`REFACTOR_REQUIRED`)** | `>= 800` 줄 | `>= 160,000` B | 대형 파일에 `+250` 줄 이상 추가 | **검수 진입 차단 (FAIL)** — 하위 모듈로 분할·리팩토링하거나 유효한 한시적 면제(Waiver) 필요 |
| **치명 (`CRITICAL`)** | `>= 1,200` 줄 | `>= 300,000` B | — | **무조건 차단 (BLOCK)** — 즉시 책임별 모듈 분리 필수 |

### 3.2 실행 명령

```bash
# 변경된 파일에 대한 복잡도 단독 측정
node .agents/skills/review-pass/scripts/measure-complexity.mjs --files <변경파일1> <변경파일2>

# 리뷰 진입 전 프리플라이트 게이트 (복잡도 + 원문 근거 점검)
node .agents/skills/review-pass/scripts/review-preflight.mjs --stage development --files <변경파일1> <변경파일2>
```

### 3.3 한시적 면제(Waiver) 규율 (`USR-012-E04`)

자동 생성 파일이나 외부 벤더 스냅샷 등 불가피한 사유로 임계치를 넘는 파일은 무단 우회할 수 없으며, 다음 필드를 모두 갖춘 만료 기한부 면제 레코드만 허용된다.

- 필수 필드: `path`, `sha256`(대상 파일 해시 고정), `maxLines`, `maxBytes`, `reason`(20~500자 구체 사유), `owner`, `authorityRef`(`source:USR-NNN#sha256:...`), `expiresOn`(최대 90일 이내 ISO 날짜)
- 파일 내용이 바뀌어 `sha256`이 달라지거나 `expiresOn`이 지나면 면제는 즉시 무효화되며, 이후 모든 리뷰 회차에서 면제 타당성을 적대적으로 재검증한다.

---

## 4. 모듈 분리 표준 절차

1. **책임 식별**: 500줄/80KB에 근접한 파일에서 (a) 순수 도메인/판단 로직, (b) 입출력·전송 어댑터, (c) 상태 저장소·잠금, (d) CLI/엔트리포인트를 분리한다.
2. **시그니처 완전성 점검 (`signature_change_completeness`)**: 함수·모듈 분리로 export/import 시그니처가 바뀌면 저장소 전체에서 호출부(`grep`/`rg`)를 전수 확인해 누락 호출부 0건을 보장한다.
3. **기존 단위·통합 시험 유지 + 분리 모듈 시험 추가**: 리팩토링 전후 외부 계약 시험이 동일하게 통과하는지 확인하고 분리된 순수 함수를 직접 시험한다.
