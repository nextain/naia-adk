# Naia ADK

**Заранее подготовленный каркас рабочего пространства для рабочих агентов кодирования ИИ.**

Когда вы пользуетесь ИИ-инструментами кодирования вроде Claude Code или Codex,
каждый инструмент хранит свои файлы правил в своём месте, а на вопросы вроде
«можно ли публиковать этот документ?» или «куда класть скиллы?» ответы находятся
от случая к случаю. Naia ADK заранее выстраивает этот каркас. Подобно тому, как
на новом ноутбуке сначала настраивают среду разработки, он вручает ИИ-агенту
прибранный рабочий стол. А панель мониторинга показывает состояние пространства
одним взглядом.

[![License](https://img.shields.io/badge/license-Apache%202.0-blue.svg)](LICENSE)

## Запуск за 5 минут

Нужны **Node 22+** и **pnpm 9+**.

```bash
pnpm install    # install workspace dependencies
pnpm dev        # run the API server (:3141) and dashboard (:3142) together
```

Откройте `http://localhost:3142` в браузере, чтобы увидеть панель. Сразу видны
три вещи:

- **Workspace** — проекты и субмодули, дерево файлов и уровень раскрытия каждого
  элемента.
- **Skills catalog** — список скиллов, зарегистрированных в этом пространстве, и
  их содержимое.
- **Settings / monitoring** — конфигурация сервера, состояние клиентов, каталоги
  данных.

Панель проксирует на API-сервер (порт 3141) только запросы `/api/portal`
представления документов. Чтобы запустить что-то одно, используйте
`pnpm dev:server` (→ 3141) или `pnpm dev:dashboard` (→ 3142). Стартовые скрипты
`./start.sh` (Linux/macOS) и `start.bat` (Windows) оба выполняют `pnpm dev`.
Серверный CLI принимает `--port`, `--host` и `--root`; например, нацельтесь на
другое пространство командой
`pnpm serve -- --root /path/to/workspace`.

## Что внутри

### Каркас рабочего пространства

Он даёт ИИ-агенту набор каталогов с фиксированными местами для всего, чтобы можно
было сразу начинать работу. Контекст для ИИ живёт в `.agents/` (английский,
JSON/YAML). Человекочитаемые руководства — в `.users/context/` (корейский) и
`.users/context/en/` (английский). Это зеркало частичное, а не полная копия: в
нём только то, что нужно читать человеку (например, скиллы канонически лежат в
`.agents/skills/`, и лишь некоторые отражены в `.users/skills/`). У скиллов,
данных и проектов есть назначенные места, поэтому пространство выглядит одинаково,
каким бы инструментом его ни открыли.

### Панель и API

Панель на Next.js визуально управляет пространством, её подпирает API-сервер на
Fastify. Вкладки **Docs** (`/docs`) и **Work** в верхней навигации показывают
общие документы компании и доску совместной работы в одном месте, а команда
`pnpm adk:setup -- --company <repo-url>` за один шаг настраивает репозитории
документов компании и проектов. Подробности настройки и использования — в
[руководстве по онбордингу](docs/guides/onboarding.en.md)
([한국어](docs/guides/onboarding.ko.md)).
Как документировать архитектуру, контракты и доказательства реализации — в
[руководстве по документации для разработчиков](docs/guides/dev-docs-writing.en.md).
API отдаёт метаданные пространства (`/api/workspace`), каталог скиллов
(`/api/skills`), портал документов компании (`/api/portal`) и WebSocket,
транслирующий события изменения файлов (`/api/ws`). Благодаря этому API к
пространству могут обращаться и другие программы, а не только панель.

### Система скиллов

Повторяющиеся задачи упакованы в переиспользуемые скиллы. Каждый скилл определён
единственным `SKILL.md`, а API-сервер сканирует `skills/`, чтобы построить каталог.
Если хотя бы один скилл нарушает формат, весь каталог падает с ошибкой
(fail-closed): вместо того чтобы молча выбросить сломанный скилл и отдать
остальное, оператор вынужден чинить его на месте. Это осознанный выбор, чтобы
случайно не отгрузить неполный каталог.

### Что сегодня в дереве скиллов

Скиллы распадаются на четыре группы. Чтобы сессия не перечитывала каждый
`SKILL.md` ради ответа «что тут есть», файл `.agents/context/skills-index.yaml`
хранит по строке на скилл: что он делает и когда к нему обращаться. Список ниже —
оглавление этого индекса.

**Документы и внешняя работа** — то, что будет читать человек.
`doc-coauthoring` (спецификации и проектные документы), `proposal-writing`,
`read-doc`, `translate-doc`, `press-release`, `weekly-report`,
`document-generation` (фирменные PDF и цифровые подписи), `copyright-reg`
(регистрация авторских прав), `patent-draft` и `patent-pipeline` (патенты),
`youtube-upload` (видео и субтитры).

**Ведение пространства** — руки, которые трогают сам репозиторий.
`project-create`, `project-migration`, `merge-worktree`, `migrate-ctx`,
`session-resume`, `sync-upstream` (синхронизация с апстримом), `manage-skills` и
`secret-vault` для шифрованного сейфа секретов.

**Проверочные гейты** — места, где требуют доказательств, а не утверждений.
`verify-implementation`, `verify-contract-conformance`, `verify-request-contract`,
`verify-product-preservation`, `verify-benchmark-contract`, `verify-review-gate`,
`verify-build` (действительно ли собирается), `verify-conflict-markers` (не
осталось ли маркеров конфликта), `verify-i18n` и `verify-hardcoded-strings`
(строки на своих местах), `webapp-testing` и `review-pass` для враждебного ревью.

**Эксплуатация и эксперименты** — работа вовне или с моделями.
`manage-discord-sessions` для Discord-шлюза, `channel-management`,
`service-management` (аптайм, затраты, инциденты), `web-monitoring`, `email`,
`sms`, `upstream-pr-review` (шлюз перед всем, что уходит OSS-мейнтейнерам),
`payroll` и `finetune-persona` для LoRA-обучения персонажей.

Новый скилл начинайте с `.agents/skills/SKILL_TEMPLATE.md` и добавляйте его строку
в индекс, когда он появится. Когда индекс разъедется с деревом, следующая сессия
пересоберёт скилл, который у неё уже был.

### Правила и минимальное управление

Даже пространству единоличного пользования нужны минимальные правила, как только
его касаются ИИ и автоматизация. Naia ADK разводит `read`, `write`, `execute` и
`publish` как отдельные concerns и прикрепляет каждому документу уровень
раскрытия. Труднообратимые действия — изменения продакшена, обращение с
секретами, публичные утверждения — отделены от обычных локальных правок и идут
через гейты согласования.

У раскрытия четыре уровня. `public` можно как есть отдавать на публичный сайт или
в open-source репозиторий; `controlled` можно делиться вовне после ревью;
`internal` остаётся внутри пространства; `confidential` покрывает чувствительные
материалы вроде договоров, учётных данных и персональных данных. Учётные данные
обычно живут вне git, но по уровню они всё равно `confidential`.

> **Гейт сессионного контракта активен в checkout без маркеров.** Несвязанная
> сессия может выполнять рутинную политику-разрешённую локальную работу: осмотр,
> `npm test`, сборки, `mkdir` и обычный недеструктивный Git stage/commit. Файлы
> управления и хост-политик, общие точки входа, сессионные контракты и авторитет
> реестра, удаление, деструктивные или удалённые команды, внешние эффекты и
> изменения продакшена по-прежнему требуют контракта. Это governance-проверка
> хуков репозитория; это не песочница операционной системы и не гарантия для
> команд, запущенных вне хуков. Политику см. в `.agents/context/agents-rules.json`
> и `.agents/context/harness.yaml`. Маркер `.codex/no-harness`,
> `.claude/no-harness` или `.pi/no-harness` в корне проекта или у предка
> наследуется потомками-checkout. Этот кандидат подключает хук сессионного
> контракта к Codex и Claude; на Pi-адаптер сессионного контракта он не претендует.

### Где живут секреты

Коммитить API-ключи и сертификаты в git нельзя. Но хранить их только на каждом
ноутбуке — значит потерять при смене машины, и никто не скажет, у кого что лежит.
Naia ADK разрубает этот узел, коммитя **ровно один файл**: папку секретов,
заархивированную и зашифрованную. Расшифрованное содержимое git вообще никогда не
видит.

Конкретно папка `key/` упаковывается в tar и шифруется с помощью
[age](https://github.com/FiloSottile/age) в единственный `key.age`. `key/` — в
`.gitignore`, так что случайно закоммитить её нельзя. Единственное, что
когда-либо попадает в коммит, — это `key.age`.

Парольную фразу вводит человек. ИИ её не получает и ни за кого не вводит. Поэтому
открытие и опечатывание сейфа происходят в собственном терминале пользователя, а
проверки и бэкап — которым фраза не нужна — можно делегировать. Эта граница
проведена покомандно внутри скилла.

```bash
bash .agents/skills/secret-vault/scripts/vault.sh init     # create a vault in a new repo
bash .agents/skills/secret-vault/scripts/vault.sh unlock   # open it (passphrase)
bash .agents/skills/secret-vault/scripts/vault.sh lock     # seal it again (passphrase)
bash .agents/skills/secret-vault/scripts/vault.sh status   # is the backup current?
bash .agents/skills/secret-vault/scripts/vault.sh sync     # commit key.age and push
```

`status` существует, потому что ошибки имеют фиксированную форму. Добавил ключ и
забыл опечатать, опечатал и забыл запушить, остался временный файл. `status`
ищет все три сразу. Когда спрашивают, забэкаплены ли ключи, отвечайте этой
командой, а не по памяти.

`lock` записывает новый шифртекст, **снова расшифровывает его для проверки** и
только потом заменяет старый файл — так недопечатанный сейф никогда не оставит
сломанный сейф.

Штатный потребитель этого паттерна — приватный репозиторий вроде `data-private`,
но подойдёт любой репозиторий с `key.age` и gitignore-нутым `key/`.
Переопределите `VAULT` и `PLAIN_DIR`, чтобы переименовать ту или иную сторону.

### LLM-адаптер (naia-anyllm)

Для функций, которым нужно обращаться к LLM, встроен адаптер `naia-anyllm`. Он
подключается через шлюз [any-llm](https://github.com/nextain/any-llm) либо
напрямую к провайдерам вроде OpenAI, Anthropic и Google. По умолчанию — аккаунт
Naia: положите ключ, выпущенный на [naia.nextain.io](https://naia.nextain.io), в
переменную окружения `NAIA_KEY`, и вы сразу сможете тратить кредиты аккаунта. Без
ключа он падает с ошибкой до любого платного вызова. Чтобы сменить провайдера
или модели, скопируйте
[`.agents/context/llm-config.yaml.example`](.agents/context/llm-config.yaml.example)
и держите API-ключи в переменных окружения или в хранилище ключей ОС, но не в
конфиге. `naia-settings/llm.json` записывает только `apiKeyRef: "NAIA_KEY"`,
никогда само значение. Если личному форку нужен долгосрочный бэкап, используйте
шифрованный age-сейф в `data-private/key/` (см. [`.env.example`](.env.example)).

Чтобы посмотреть поддерживаемые модели и актуальные цены, а также переводить
длинные PDF, используйте скилл `translate-doc`. Справочники моделей и цен
работают без ключа; перевод сначала показывает оценочную стоимость и умеет
продолжаться с места остановки.

## Почему устроено так

### Формат — это контракт

Сердце Naia ADK — не конкретный инструмент, а **формат**. Раскладка каталогов
(`.agents/`, `.users/`, `skills/`, `data-*/`) и схемы файлов
(`agents-rules.json`, `SKILL.md`) — фиксированное соглашение, и любой инструмент,
умеющий его читать, может потреблять то же пространство. Claude Code, Codex,
opencode, naia-agent, agy и muse читают одно и то же пространство, не встраивая
код друг друга. Так что инструменты можно менять или сочетать, а пространство
продолжает работать.

И само enforcement правил не зависит от инструментов. Хосто-нейтральное ядро
(`.agents/hooks/core/`) и политики (`.agents/hooks/policies/`) одинаково движут
и хуками Claude Code, и pi-расширением.

### Сначала личная база, потом рост в команду

Naia ADK строго однопользовательский, для личного пользования. Оргструктуры
компаний, правила тенантов и цепочки делегированных согласований относятся к
более высокому слою. Что он даёт — так это единственное место, где записать
контекстную дисциплину, прежде чем пространство вырастет до масштаба команды или
компании.

Для командной работы и общих знаний можно выбрать опциональную
организационную линейку, представленную
[Naia Business ADK](https://nextain.io/adk). Она добавляет управление активами,
процессами и доступами, владение команды и делегированные согласования.

### Линейки форков

Naia ADK задуман так, чтобы форкаться в ваше собственное пространство. Частные
лица могут форкать `naia-adk` напрямую. Организация может выбрать отдельную
организационную линейку вроде `naia-business-adk` для пространств компании и
сотрудников. Единая фиксированная цепочка не требуется никому.

```
naia-adk                  ← public personal base (Apache 2.0)
  └── {user}-adk          ← direct personal fork

naia-business-adk         ← optional organization lineage
  └── {org}-adk            ← org fork: company data + business submodules
        └── {member}-adk    ← member workspace derived from the organization
```

Внутренняя линейка Nextain — отдельный эксплуатационный пример. Публичный
пользователь может держать прямой личный форк и назвать его `{user}-adk` по имени
аккаунта.

Если нужна проектно-командная база, можно выбрать
[naia-pj-adk](https://github.com/nextain/naia-pj-adk) как отдельную базу. PJ —
база-адаптер для многопроектного дрейфа контекста, стоимости вызовов и границ
эксплуатации Discord. Кастомизация личного форка и правила ролей/рабочего времени
команды — отдельные заботы. Помогать организовывать и прослеживать эту работу —
цель дизайна этой структуры, а не измеренная гарантия экономии затрат или
сокращения сроков. База PJ — не родительский репозиторий личного форка.
`naia-business-adk` — когда нужно организационное сотрудничество — опционален.

## Структура

Репозиторий делится на рантайм-код (`packages/`), правила и контекст (`.agents/`,
`.users/`), скиллы (`skills/`, `.agents/skills/`) и каталоги данных, которые
заполняет каждый форк.

| Directory | Purpose |
|-----------|---------|
| `.agents/` | Контекст для ИИ (английский, JSON/YAML) — единый источник истины для правил |
| `.users/context/` | Человекочитаемые руководства (корейский, Markdown) |
| `.users/context/en/` | Английское человекочитаемое зеркало (Markdown) |
| `.claude/` | Конфиг Claude Code, хуки, симлинки скиллов |
| `skills/` | Операционные/рантайм скиллы (отдаёт API панели) |
| `scripts/` | Утилитарные скрипты |
| `templates/` | Шаблоны документов |
| `docs/` | Архитектурные доки, проектные спецификации |
| `packages/` | Рантайм-пакеты (pnpm workspace) |
| `config/` | Примеры профилей воркеров и конфиг деплоя |

### Рантайм-пакеты (packages/, всего 12)

Три — реально работающие программы; остальные — тонкие пакеты, задающие форматы
и спецификации.

- `core` — движок, разбирающий пространство и скиллы.
- `server` — Fastify REST/WebSocket API.
- `dashboard` — панель на Next.js.
- `skill-spec` — инструменто-независимый контракт формата скиллов
  (`SkillDescriptor`, `SkillLoader`).
- `skills-builtin` — общий каталог скиллов.
- `openclaw-compat` — инструмент миграции скиллов OpenClaw в формат naia.
- `persona` — спецификация конвенции системного промпта.
- `process` — спецификация паттернов workflow (ревью → решение → выполнение,
  разработка от issue и так далее).
- `naia-anyllm` — адаптер LLM через шлюз any-llm / прямых провайдеров.
- `artifacts-spec` — стандартная схема артефактов разрешений (RBAC) и жизненного
  цикла разработки (SDLC). Определяет 15 типов артефактов как JSON Schema и для
  каждого указывает, трекается ли инстанс git-ом или ограничен сессией.
- `ax-messenger` — пакет реле/админки мессенджера Matrix (ИИ-реле, леджер и
  провайдеры поверх `matrix-js-sdk`).
- `benchmark-contract` — постоянные контракты бенчмарков и governance-доказательств,
  общие для `naia-adk` и `naia-agent`.

### Уровни воркеров и переопределения ревьюеров

Роли и модели настраиваются раздельно — никакая версия модели не зашита в
архитектуру.

- `config/tier-profile.example.json` (`tier-profile/v1`) — моделенезависимый
  4-уровневый профиль воркеров. Уровни описывают *роли* (лёгкие проверки, дизайн и
  реализация, ролевые сессии, независимое ревью); кандидаты каждого уровня
  привязывают CLI и модель раздельно, так что смена модели никогда не меняет
  структуру ролей.
- Переопределения ревьюеров гейтов согласования живут в инстансном
  `.claude/deploy/config.json` как `review_models` (id ревьюера → точная модель,
  минимальный effort, раннер). Применяются только после согласования `CFG-`; без
  согласованного конфига действуют дефолты кода. Раннеры включают `agy`, `muse`,
  `codex` и `claude`. См.
  [гайд по гейту плана согласования](docs/guides/approval-plan-gate.en.md).
- `naia-settings/review.json` хранит кросс-репозиторную панель ревью и политику
  уровней моделей, потребляемые скиллом `review-pass` и `naia-agent`.

### Каталоги данных (gitignored, заполняются в каждом форке)

Эти четыре никогда не коммитятся. Кто форкает репозиторий, заполняет свои данные.

| Directory | Scope | Content |
|-----------|-------|---------|
| `data-company/` | Company | Общефирменные документы, общие ресурсы |
| `data-teams/` | Team | Документы команд (стратегия, учёт и т.д.) |
| `data-private/` | Personal | Личные данные, env-файлы, приватные доки |
| `projects/` | Personal | Репозитории проектов (субмодули) |

### Два дерева скиллов

Скиллы живут в двух местах, их потребляют разные стороны.

- `.agents/skills/` — скиллы ИИ-ассиста и workflow. Claude Code пользуется ими
  через симлинк `.claude/skills/`. Включая ревью (`review-pass`), верификацию
  (`verify-implementation`), слияние worktree (`merge-worktree`), извлечение
  документов (`read-doc`), бизнес-скиллы вроде патентов/копирайта/зарплаты и
  прочие вроде `finetune-persona`, `secret-vault` и `youtube-upload`.
- `skills/` — операционные/рантайм скиллы. API-сервер сканирует
  `skills/**/SKILL.md` и отдаёт их панели. Сюда входят отправка
  email/SMS/уведомлений, управление каналами, мониторинг сервисов и веба,
  генерация документов; `skills/business/` держит орг-скиллы вроде
  `press-release`.

Самый точный список — каталог скиллов в панели. Текстовая таблица — в
[индексе скиллов](.agents/context/skills-index.yaml).

## Начало работы

### Личное

1. Форкните `naia-adk` в свой аккаунт (приватно, если можно).
2. Клонируйте: `git clone https://github.com/YOUR-USER/your-adk.git && cd your-adk`
3. Добавьте апстрим: `git remote add upstream https://github.com/nextain/naia-adk.git`
4. Создайте каталоги данных: `mkdir -p data-private projects`
5. Добавьте проекты, настройте `.agents/` и начинайте работу.
6. Если пользуетесь ресурсами аккаунта Naia, задайте `NAIA_KEY` как переменную
   окружения.
7. Регулярно синхронизируйтесь: `git fetch upstream && git merge upstream/main`

### Компания

1. [Свяжитесь с нами](https://nextain.io/contact) для доступа к `naia-business-adk`.
2. Приватно форкните `naia-business-adk` в аккаунт организации, затем клонируйте.
3. Добавьте апстрим: `git remote add upstream https://github.com/nextain/naia-business-adk.git`
4. Заполните данные компании и субмодули проектов: `mkdir -p data-company projects`,
   `git submodule add <repo> projects/<name>`
5. Каждый участник снова форкает орг-ADK как личное пространство.

### Интеграция Naia Shell (опционально)

Если пользуетесь десктоп- и веб-приложением [Naia Shell](https://github.com/nextain/naia-shell),
нацельте его путь пространства на ваш каталог ADK. Скиллы и данные отдаются через
API.
