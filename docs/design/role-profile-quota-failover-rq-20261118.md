# 역할별 ADK 프로파일과 한도 대체 실행 — 요구사항

## 적용 범위

이 요구사항은 Naia ADK의 공통 실행 규칙·관문과 각 kind: agent 프로파일의 경계를 정한다. 공개 기본값에는 특정 회사·사람·모델·계정 값이 들어가지 않는다. 실제 후보와 계정 참조는 각 비공개 에이전트 ADK에 둔다. 사용자 요청에서 언급한 현재 실물 목록은 구현 시험 때 격리된 입력으로만 쓰며, 이 공개 저장소 문서에 개인·계정 식별값을 복사하지 않는다.

근거 구조는 docs/guides/adk-2.0-structure.md, schemas/adk-manifest.schema.json, templates/agent-skeleton/, templates/group-skeleton/이다. 스키마의 supported_kinds 기본 집합은 user·agent·project·group이며 org는 하위 호환용 별칭이다. 각 인스턴스의 adk.json은 한 kind를 선언한다.

## 요구사항

### RQ-01 — 한도 감지, 대체 실행과 복귀

**근거 원문**

> “리밋 다됬을때 다른 대안으로 변경되고 풀리면 돌아와야 하는거 아냐 ?”
>
> “각 층에서 우선순위가 있는 페일오버면, 해당 층에서 페일되면 다른 프로파일로 바꾸고, 우선순위가 높은게 복구되면 다시 돌아오게”

**수용 기준**

1. 실행 어댑터가 제공자 응답을 구조화된 사건으로 바꾸고, 한도 소진·일시 제한·인증 오류·네트워크 오류·알 수 없는 실패를 구분한다. 모호한 실패는 복구로 간주하지 않는다.
2. 3층은 에이전트 프로파일의 명시된 우선순위 순서대로 다음 사용 가능 후보로 이동한다. 2층 후보 선택 방식은 RQ-02를 따른다.
3. 상위 우선순위 후보 복귀는 제공자의 권위 있는 사용 가능 신호 또는 프로파일에 정한 성공한 복구 확인 중 하나(`any_of`)로 증명한다. 둘 다 요구하는 `all_of`로 해석하지 않는다. 경과 시간, 시각 타이머, Retry-After의 도래만으로 복구 처리하지 않는다.
4. 제공자 이벤트가 없는 어댑터는 다음 작업 admission 때 상위 후보의 상태 API를 조회한다. 상태 API가 없으면 범위 잠금에서 비용·부작용 없음이 승인된 복구 probe만 같은 admission 흐름에서 시도한다. 안전한 조회 수단이 없으면 자동 복귀를 차단 상태로 유지하고 주기 타이머로 대체하지 않는다.
5. 실행 중인 작업은 중단 전에 진행 상태와 결과를 기록한다. 복귀는 안전한 작업 경계에서 수행하고, 미완료 작업을 성공으로 표시하지 않는다.
6. 모든 후보가 막히거나 복구 신호를 확인할 수 없으면 작업을 대기·차단 상태로 남기고 그 이유를 기록한다. 무한 재시도나 빈 성공 결과를 만들지 않는다.

### RQ-02 — 층별 역할과 에이전트별 프로파일

**근거 원문**

> “각 층간 우선순위가 있는 페일오버 (3층), 혹은 동등 수준 랜덤 선택(2층)”
>
> “각 에이전트별 프로파일 설정할 수 있게하고”
>
> “3층은 오케스트레이션과 서브에이전트들이 제대로 돌아가는지 드리프트 일으키지 않는지 보고 유저와 소통하는거야”

**수용 기준**

1. 역할 프로파일은 kind: agent ADK 단위로 분리한다. Naia 업스트림은 공통 스키마·실행기·훅 구현을 제공하고, 그룹 ADK는 공통 정책·관문 설정·전역 상태를 둔다. 그룹 ADK는 개별 모델·계정 후보 목록의 정본이 되지 않는다.
2. 3층은 조정·위임·실행 상태와 드리프트 감시·결과 판정·사용자 소통을 맡고 직접 구현 작업을 수행하지 않는다.
3. 3층 프로파일은 우선순위가 명시된 후보 사슬을 가진다. 해당 후보가 명확한 한도 소진 상태일 때만 다음 사용 가능 후보를 고른다.
4. 2층 프로파일은 우선순위 숫자 없이 현재 사용 가능한 동등 후보에서 균등 무작위로 고른다. 중복된 후보 참조는 한 후보로 계산한다.
5. 프로파일이나 선택 방식이 없거나 유효하지 않으면 실행을 시작하지 않는다.

### RQ-03 — 개발과 독립 리뷰어 분리

**근거 원문**

> “2층은 개발과 리뷰어 분리하고”
>
> “리뷰는 다른 에이전트가 해야해”
>
> “코드를 믿을수 있는건 설계대로 테스트 되었을때 뿐이야”

**수용 기준**

1. 개발자와 리뷰어는 서로 다른 agent_id를 사용한다.
2. 리뷰어는 개발자가 사용한 모델 계열과 다른 프로파일만 선택할 수 있다. 둘을 분리할 후보가 없으면 리뷰를 생략하지 않고 완료 판정을 막는다.
3. 리뷰 작업은 개발 작업과 별도 작업 단계·실행 기록을 가지며, 리뷰 결과가 없는 구현은 통과로 표시하지 않는다.
4. group ADK가 개발자·리뷰어 각각의 agent_id를 배정하고, 두 agent ADK는 서로 독립된 로컬 후보 사슬을 가진다. 리뷰어도 agent ADK의 프로파일과 공통 실행 관문을 통과한다.

### RQ-04 — ADK 실행기만 일꾼·역할 세션을 시작

**근거 원문**

> “무슨 프롬프트로 하드코딩 하지 말고 말이야”
>
> “그러라고 프로파일 만들었잖아.”
>
> “누가 점검하래”, “막으라고 했지”, “adk는 그걸 막는거잖아”

**수용 기준**

1. 역할 세션과 일꾼은 역할 ID·agent ID·작업 ID를 받아 프로파일을 읽는 ADK 실행기만 시작한다. 역할 시작 대본은 이 참조만 전달하고 agent ADK의 persona 참조로 역할 지시를 읽는다. 모델·도구 선택이나 층 역할 설명을 명령·인라인 시스템 프롬프트에 고정하지 않는다. 작업 입력은 프로파일 설정을 덮어쓸 수 없다. 역할 세션 launcher는 Claude CLI를 실행하기 전에 프로파일과 문서 gate를 검증한다.
2. 직접 모델·도구 명령, 인자에 박은 모델·도구 선택, 프로파일보다 우선하는 CLI 인자·환경 덮어쓰기, 허용 목록 밖 실행 대본은 모든 ADK 관리 진입점에서 차단한다. 프로파일은 도구 정책 참조를 가지며 허용 도구와 도구 체인의 정본은 agent ADK의 참조 정책 파일이다. 차단은 정적 검색 보고만으로 대체할 수 없다.
3. Claude Code 세션에서는 `.claude/settings.json`의 `hooks.PreToolUse`에 실행 관문을 등록한다. 현재 `Bash|shell_command|Edit|Write|NotebookEdit|apply_patch` matcher와 `Task|Agent` matcher에 프로파일 차단 훅을 추가하고 기존 훅을 보존한다. 관리 설정의 정확한 검증 binary/build allowlist에 든 버전만 허용하며, 해당 버전은 `onFailure: "block"` 지원 최소 버전인 Claude Code v2.1.295 이상이어야 한다. launcher는 실제 실행 binary의 version/build와 유효한 `onFailure: "block"` 등록을 CLI 실행 전 확인한다. allowlist 밖 버전·버전 확인 실패·설정 누락은 시작 차단이다. 차단 응답은 exit code 2 또는 exit 0과 유효한 명시적 `deny`여야 한다.
4. Claude Code의 `Task|Agent` 네이티브 spawn은 모두 PreToolUse에서 거부한다. 이 훅은 네이티브 spawn을 외부 ADK 실행기로 재라우팅하지 않는다. 하위 일꾼은 ADK 실행기가 시작한 별도 세션만 허용한다. PreToolUse는 Claude Code 도구 호출에만 적용되므로 systemd, 직접 셸·터미널 등 ADK 밖 시작까지 보호한다고 주장하지 않는다.
5. ADK 관리 진입점인 역할 세션 launcher, worker-runner, supervisor는 같은 profile executor를 호출한다. 실행기·필수 훅 등록·프로파일 검증이 누락되거나 오류·시간 초과가 나면 CLI·worker·pane을 만들지 않는다. OS 수준에서 ADK 밖 직접 provider CLI 실행까지 막을지는 별도 범위 결정이다.
6. 대본 안의 간접 실행, 별칭, 체인 실행과 동적 명령 구성도 시험한다. 훅이 호출 경로를 증명할 수 없거나 실행 파일을 안전하게 확인할 수 없으면 차단한다.
7. worker-runner·역할 세션 launcher·supervisor는 ADK executor 서명으로 검증되는 자기 audience용 일회용 launch ticket만 받는다. ticket은 작업·단계·admission·agent·profile·tool-policy digest·문서 입력 묶음 digest·독립 적대 검수 evidence digest·그 두 digest를 승인한 현재 범위 잠금 digest에 묶인다. 문서 입력 묶음은 업무 카드/RQ/PL/시험 계획과 적용 가능한 PC·SP·UC·FE 원문 또는 승인 전 N/A 제안 disposition manifest만 포함하며, 검수 evidence와 사람 승인 범위 잠금은 포함하지 않는다. 검수 evidence는 입력 묶음 digest를 대상으로 하고, 범위 잠금은 입력 묶음 digest와 검수 evidence digest를 승인한다. 이 단방향 digest 사슬로 자기참조를 금한다. redemption 때 group 원장의 최신 입력 묶음·검수 evidence·잠금·active admission/stage와 원자적으로 대조해 nonce를 한 번만 소비한다. 묶음 문서 변경·누락·오래된 검수/잠금·취소된 admission·다른 audience·재사용 ticket은 process 생성 전에 거부한다.

### RQ-05 — 문서·검수·범위 잠금 없이는 구현 일꾼을 시작하지 않음

**근거 원문**

> “ADK는 PL 부터 UT까지”
>
> “코드를 믿을수 있는건 설계대로 테스트 되었을때 뿐이야”
>
> “업무 카드와 RQ·PL·시험 계획 문서가 없으면 구현 일꾼을 띄우지 못한다.”

**수용 기준**

1. 구현 일꾼을 시작하기 전에 업무 카드, RQ, PL, 시험 계획이 모두 있고 서로 같은 작업 ID와 요구 ID를 가리키는지 검사한다.
2. 선행 입력 manifest는 업무 카드·RQ·PL·시험 계획과 PC·SP·UC·FE 각각의 원문 경로·digest 또는 승인 전 N/A 제안(근거·owner·재검토 조건)을 연결한다. `document_bundle_digest`는 이 입력 manifest만 정규화해 계산하며, 독립 적대 검수 evidence와 사람 승인 범위 잠금은 포함하지 않는다. 검수 evidence는 대상 `document_bundle_digest`를 기록하고, 범위 잠금은 정확한 입력 digest와 검수 evidence digest 및 disposition 결정을 승인한다. launcher ticket은 입력 묶음·검수 evidence·범위 잠금 각각의 digest를 별도 claim으로 묶는다. 이 순서에서 승인 기록은 입력 digest의 구성원이 아니므로 순환 참조가 없다. 최신 입력 manifest·검수 evidence·범위 잠금이 없거나 하나라도 낡았으면 시작을 막는다.
3. 정본 파이프라인의 PC·SP·UC·FE 원문 여부를 확인한다. 이번 요청에서 만들도록 지정되지 않은 문서는 임의로 생략 처리하지 않는다. 범위 잠금은 각 항목의 원문 경로와 digest 또는 N/A disposition·근거·owner·재검토 조건의 digest를 명시적으로 승인해야 한다. disposition 후보를 수정하면 새 입력 묶음·재검수·새 범위 잠금 전까지 구현 시작을 막는다.
4. 누락·잘못된 연결·읽기 실패·검수 실패는 모두 차단으로 판정한다. 본문에 “완료” 문구만 있거나 파일 이름만 있으면 통과하지 않는다.

### RQ-06 — 중복 작업과 모델·계정 쏠림 차단

**근거 원문**

> “같은 일을 다시 띄우기, 한 모델·계정에 몰기를 막는다(2층 동등 랜덤 선택, 리뷰는 개발과 다른 모델).”

**수용 기준**

1. 작업 ID·역할·단계로 중복 방지 키를 만든다. 이미 실행 중인 키는 새 프로세스를 만들지 않고 기존 실행을 돌려준다. 끝난 작업을 다시 시작하려면 원 작업 참조, 회차 번호와 이유가 붙은 명시적 재시도만 허용한다.
2. 2층 후보 선택은 프로파일별 모델 계열·계정 참조의 중복을 제거한 뒤 동등 후보에서 균등 무작위로 한다.
3. 그룹 정책은 여러 agent ADK에 걸친 활성 실행 수와 분배 묶음별 할당을 모델 계열·계정 참조·프로파일 각각으로 제한한다. 제한값은 인스턴스에서 명시하고 누락되면 fail-closed 한다. 한도를 넘는 후보는 제외하고, 적격 후보가 없으면 새 프로세스를 만들지 않는다.
4. 분배 묶음의 작업 수를 `N`, 해당 축의 적격 고유 용량 단위를 `K`라 할 때 단위당 상한은 `ceil(N/K)` 이하로 한다. 이는 프로파일, 모델 계열, 계정 참조에 각각 적용한다. 한도 소진으로 적격 후보가 바뀌면 미실행 작업만 남은 후보로 다시 나눈다.
5. 개발과 리뷰가 같은 agent나 같은 모델 계열을 고르지 않는다. 실행 기록에 실제 선택된 agent_id, 프로파일 참조, 모델 계열 참조, 계정 참조와 분배 묶음 ID가 남는다. 비밀값 자체는 기록하지 않는다.

## 완료 범위와 보류 항목

이 RQ는 요구 정의다. 실제 제공자별 한도 신호·복구 확인 방식, 그룹 내 계정 용량값, 각 역할의 구체 프로파일은 PL의 열린 결정에 남긴다. 문서 적대 검수와 사람 범위 승인 전에는 이 요구를 구현 이슈나 실행 승인으로 해석하지 않는다.

## 정본 간 차이와 결정 대기
