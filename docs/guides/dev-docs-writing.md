# 개발 문서 작성 기준

이 기준은 공개 Naia ADK의 아키텍처, 계약, 절차, 참고 자료를 작성하고 검토할 때 적용한다. 개발 문서는 사람과 AI가 같은 코드와 계약을 근거로 동작을 설명하도록 돕는다. 각 주제의 현행 기준은 저장소 안 정본 문서 한 곳에서 관리한다.

문서의 폴더 배치, 목차, 파일 이름, 기록 보관, 이동과 링크 관리는 저장소의 기존 관례를 따른다. 대외 문장과 어조는 [대외 글 작성 기준](external-writing.md)을 따른다.

## 문서의 역할

기존 정본을 먼저 찾고 그 문서를 갱신한다. 문서 종류마다 답할 질문과 표현을 구분한다.

| 문서 종류 | 답하는 질문 | 표현 |
|---|---|---|
| 아키텍처 | 시스템의 목적, 경계, 구성 요소와 연결은 무엇인가? | 배경과 구조를 산문과 필요한 그림으로 설명한다. |
| 계약·인터페이스 | 구성 요소 사이에 어떤 입력, 출력, 상태, 실패 약속이 있는가? | 스키마를 연결하고 필드·상태·전이를 표로 설명한다. |
| 절차 | 어떤 순서로 작업하며 성공을 어떻게 확인하는가? | 번호가 있는 단계와 관측 가능한 완료 조건을 쓴다. |
| 참고 자료 | 어떤 명령·설정·파일·상태를 찾아야 하는가? | 저장소에서 확인한 값을 연결하고, 생성 가능한 값은 검증된 결과를 쓴다. |
| 결정 기록 | 어떤 선택을 했고 결과가 무엇인가? | 저장소가 정한 위치의 기록을 연결하며 현행 계약의 정본을 유지한다. |
| 작업 기록 | 특정 시점에 무엇을 조사·측정·검토했는가? | 기록의 시점과 관측 결과를 밝히고 현행 기준과 구분한다. |

현행 정본은 현재 동작을 설명한다. 작업 기록은 특정 시점의 확인 결과를 보존한다. 구현 기준이 바뀌면 정본을 갱신하고, 기록에는 확인 당시의 범위를 남긴다.

## 페이지 앞머리와 기준판

사람이 읽는 개발 문서는 제목 앞에 다음 세 줄을 둔다.

```text
이 문서가 답하는 질문: <독자가 확인할 질문>
상태: <현행 기준 또는 시점이 있는 기록 상태>
기준판: 공개 저장소 `<전체 커밋 SHA>`
```

기준판에는 검토한 공개 기준판의 전체 커밋 SHA를 기록한다. 버전과 짧은 SHA는 읽기 쉬운 설명에 함께 쓸 수 있다. 재현 가능한 근거는 전체 SHA로 고정한다. 현행 동작은 확인한 기준판의 근거로 설명한다.

적용 범위를 구분해야 할 때는 본문에서 공통 기준인지 특정 배포 환경인지 밝힌다. 접근 권한과 정보 노출 등급은 저장소의 관련 기준에 따라 별도로 기록한다.

## 계약 설명

계약 문서는 독자가 확인할 경계와 약속을 설명한다. 해당 내용이 계약에 적용될 때 기록한다.

1. 목적과 참여자를 설명하고, 누가 계약을 만들고 소비하는지 밝힌다.
2. 데이터 필드의 형식·필수 여부·기본값·제약을 정본 스키마에 연결한다. 독자가 비교할 보충 정보는 표로 정리한다.
3. 상태가 있는 계약은 허용 전이, 거부 조건, 관측 결과를 설명한다.
4. 구현과 직접 관련된 시험을 저장소 상대 경로와 심볼로 연결하고, 재현할 확인 명령을 적는다.
5. 독립된 변경 이력이 필요한 문서는 저장소의 기존 관례를 따른다.

표와 본문은 스키마의 필드 의미와 사용 맥락을 설명하고, 필드 정의는 스키마에서 확인하도록 연결한다. 검사 결과에는 명령, 실행 시점, 종료 상태 또는 관측 결과를 남긴다. 실행한 검사 결과와 미실행 항목을 구분해 기록한다.

## 사실 근거와 코드 연결

변하기 쉬운 구현 근거는 저장소 상대 파일 경로와 심볼·함수·스키마 키를 함께 기록한다. 예를 들어 `scripts/lib/adk-manifest-validator.mjs`의 `validateAdkManifest`를 연결한다. 줄 번호는 검토 중 위치를 찾는 보조 정보로 쓰고, 정본의 근거는 파일 경로와 심볼로 고정한다.

수치, 버전, 포트, 기본값, 경로, 허용 상태는 해당 기준판의 코드·스키마·설정에서 확인한다. 코드와 실행 관측이 다르면 각각의 근거와 차이를 구분해 설명한다. 책·회의·메시지·작업 기록은 배경을 설명하고, 현행 구현은 기준판의 코드·스키마와 필요한 실행 관측으로 뒷받침한다.

자동 검사는 형식·링크·파일·스키마 존재와 기계 비교가 가능한 값을 확인한다. 주장의 의미가 코드로 뒷받침되는지, 공개 문서에 적합한지는 내용 검토에서 확인한다. 검사 범위에 맞춰 결과를 설명한다.

## 읽기와 구조

제목과 첫 문단에서 독자가 해결할 질문을 밝힌다. 결론과 필요한 범위를 먼저 설명하고, 이유와 세부 사항을 이어 쓴다. 필드·상태·책임·비교 항목처럼 행과 열의 대응이 중요한 정보는 표로 표현한다. 배경과 예외는 산문으로 설명한다.

절차는 번호가 있는 순서로 쓴다. 호출 흐름은 읽을 수 있는 그림으로 표현하고, 화살표와 경계가 뜻하는 바를 본문에서 설명한다. 공통 용어는 [용어 기준](../../.agents/context/terminology.yaml)에 맞추고, 프로젝트 고유 용어는 해당 프로젝트의 용어 정본에 연결한다.

## 공개 근거와 검토

공개 문서의 역할·경로·계약·예시는 공개 저장소에서 확인할 수 있는 근거를 사용한다. 예시는 저장소의 공개 예제나 실제 인스턴스와 무관한 재현 가능한 값으로 구성한다.

새 정본이나 계약 동작을 설명할 때는 코드와 스키마의 근거를 대조하고 변경 범위에 맞는 독립 검토를 거친다. 권한, 데이터, 보안 또는 여러 모듈에 걸친 계약은 저장소의 검토 절차를 따른다. 변경 뒤에는 문서 링크와 자동 검사 결과를 확인한다. 검사에서 뒤처짐 후보가 나오면 관련 코드와 주장을 다시 대조해 문서 내용을 갱신한다.

## 사례집과 개발 문서

사례집은 기준이 생긴 배경과 적용 사례를 설명한다. 개발 문서는 현재 구조·계약·절차의 정본이다. 책에 적힌 코드 인용은 책이 밝힌 시점의 사례로 읽는다. 책에서 현재 동작을 안내할 때는 해당 개발 문서에 연결한다.
