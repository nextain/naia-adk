# 디버그 모드와 로그 원칙

모든 naia 프로젝트가 물려받는 개발 원칙이다. 규칙 줄은
`.agents/context/agents-rules.json` 의 `conventions.debug_observability` 에
있고, 이 문서는 배경과 적용 방법을 적는다.

## 배경

2026-10-14 저장소 소유자 지시 원문:

- "흠.. 디버그 모드를 아예 고려 안하고 있네" / "개발의 기본인데"
- "모든 배치와 모듈에는 로그 심어"
- "해당 로그는 주기적으로 지우는 배치 만들고"
- "지금 우리 서비스 자체가 디버그가 없으면 원인 찾는데 오래걸리는 서비스야"
- "전체적으로 다 해당 기능을 넣고, 디버그모드의 on/off 기본은 모두 on 로그 삭제에 대한 배치를 두어서 용량 관리해"
- "naia 개발 원칙에 추가해"

naia 서비스는 여러 모델·외부 제공자·미디어 처리 단계를 거치므로, 실패가
나면 어느 단계에서 무엇이 들어가고 나왔는지 남아 있지 않으면 원인을 찾는 데
오래 걸린다. 그래서 로그와 디버그 모드는 나중에 붙이는 기능이 아니라 처음부터
갖추는 기본이다.

## 원칙

1. **모든 서비스·배치·모듈에 로그를 심는다.** 시작·끝·소요 시간·입력 요약·결과
   요약·실패를 구조화된 형식(한 줄 JSON 등)으로 남긴다. 한 요청·작업을 끝까지
   따라갈 수 있게 작업 식별자를 함께 적는다.
2. **디버그 모드를 둔다. 기본값은 켜짐이다.** 설정이나 환경 변수 하나로 끌 수
   있어야 하며, 끄는 것은 명시적 선택이다.
3. **실패 사유는 자르지 않는다.** 예외 메시지·스택·외부 응답 본문을 전체로
   남긴다. 요약만 남기면 원인을 다시 재현해야 한다.
4. **중간 산출물은 디버그 모드에서 보존한다.** 단계별 입력·출력(프롬프트, 중간
   파일 경로, 변환 결과 메타데이터 등)을 디버그 보존 위치에 둔다.
5. **모든 로그·디버그 보존물에는 정리 배치를 둔다.** 보존 기간과 용량 상한을
   정하고, 주기적으로 오래된 것부터 지우는 배치를 함께 만든다. 정리 배치 자체도
   무엇을 몇 개·몇 바이트 지웠는지 로그를 남긴다.
6. **넣지 않는 것.** 비밀 값·토큰·인증 정보·개인정보, 원본 미디어 바이트(음성·
   영상·이미지 원본)는 로그에 넣지 않는다. 미디어는 경로·크기·해시·길이 같은
   메타데이터만 남긴다.

## 적용 점검

새 서비스·배치·모듈을 만들거나 기존 것을 고칠 때 다음을 확인한다.

- 로그 출력 위치와 형식이 정해져 있는가
- 디버그 모드 설정 항목이 있고 기본값이 켜짐인가
- 실패 경로에서 사유 전체가 남는가
- 로그·디버그 보존 위치마다 보존 기간·용량 상한과 정리 배치가 있는가
- 비밀·개인정보·원본 미디어 바이트가 로그에 섞이지 않는가
