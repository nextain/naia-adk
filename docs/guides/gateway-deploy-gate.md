# Gateway runner gate

The six files in `scripts/gateway-runner/` are a single versioned bundle. Sync the upstream bundle to the operator checkout as described below; plans pin each required file and the gate checks its upstream fingerprint. Service policy must also explicitly allow the exact command and the plan must pin that command.

A plan may declare `environment_additions` as an array of `{ "name", "source_id" }` objects. The only pairs are `AZURE_TTS_KEY` / `azure-tts-key-v1` and `AZURE_TTS_REGION` / `azure-tts-region-v1`, in that order. No values belong in the plan. The launch command is `bash /absolute/path/launch-local.sh prod RUN_ID TAG DIGEST CURRENT REVISION backup ADDITIONS`, where ADDITIONS is the ordered comma-separated source IDs or `-` for none. Cleanup uses the same tag, digests and revision with `cleanup` and either no ADDITIONS argument or `-`. The gate binds the declaration, arguments, pinned files, service, run ID and image declarations. Existing launch commands without additions retain their previous meaning.

`bash /absolute/path/status-local.sh prod RUN_ID env-names` is an independent read of the six fixed names; RUN_ID still follows the normal syntax but no run history is needed. Its output reports only ABSENT, EMPTY, or PRESENT. Install and verify the new remote runner under a separately approved operating plan before using it.

Run `.agents/scripts/plan-cmd-check.cjs PLAN STEP COMMAND KIND [CANDIDATE]` from the policy root for an offline preflight of the same classifier and binding checks. It does not grant approval or replace the execution gate. After this change is merged upstream, each ADK fork follows `.agents/skills/sync-upstream/SKILL.md`: inspect drift, run the normal fetch/merge and version stamp from its immediate upstream, review the result, then sync the next fork down the chain. This carries the gate, CLI and complete runner bundle together. Adapt `config/deploy-gate.example.json` into the instance-owned `config/deploy-gate.json`, review and track that policy in the instance configuration, including its exact allowed commands and service settings. Verify the synchronized six-file fingerprints and policy before use. Upstream synchronization does not install the remote VM runner; that requires a separate approved operating plan.

Nonempty `environment_additions` requires exactly one gateway `backup` launch with the same ordered source IDs; independent reads and unrelated service plans cannot declare additions. Cleanup can be planned alone or with a different run ID; it runs the staged bundle without installing it. The example policy's `requiredFiles` paths assume the bundle is under `scripts/gateway-runner` in the policy root; adjust the paths when installing the bundle elsewhere.

The offline preflight does not check all referenced-file pins for non-gateway custom commands. Review and execution gates perform that check. Installing the remote runner with `backup` requires `kind: feature`, including the feature test and code gate receipts; the independent `installed-hashes` check uses `kind: ops`. Plan those separately and satisfy the feature readiness requirements before installation.
