# 부를 때와 답할 때 멘션

특정 사람·에이전트에게 향하는 질문·부탁과 그 사람의 글에 다는 답글에는 기본적으로 본문에 상대의 플랫폼 멘션(예: 디스코드 `<@ID>`)을 넣는다. 남의 부탁·질문에 대한 받음 답과 결과 답에는 상대 멘션과 원문 또는 받음 답에 대한 답글 참조를 함께 둔다. 답글 참조는 추적 연결 증거일 뿐 알림·깨움 신호가 아니며, 이름 호칭도 그 자체로 상대에게 알림을 보내지 않는다. `[A → B]` 머리글과 `B에게`·`B께`·`- B:` 호칭은 추적기에 답할 의무를 만들 수 있지만 멘션을 대신하지 않는다.

받는 사람 없는 공지와 남의 부탁·질문과 무관한 자기 글 답글만 예외다. 특정 상대에게 하는 부탁이나 결과를 공지 또는 자기 글 답글로 꾸며 멘션을 피해서는 안 된다. `outsideCall: mention-or-name`, `response-watch`의 `all-human`, `requireMentionInReply: false`, 별도 권한을 설정한 중계기의 이름 감지는 인스턴스에서 명시적으로 켠 경우에만 해당 범위를 넓히는 예외다. 기본은 멘션 필수다.

멘션은 상대에게 알림을 보내고 에이전트의 깨움을 시작하는 신호다.
이름만 쓴 글은 상대가 제때 읽지 못할 수 있다. 역할 이름과 멘션 대상은 인스턴스 설정으로 정한다.

## 부탁하기

상대 멘션과 글 머리 `[보내는 이 → 받는 이]`를 함께 쓰고, 부탁할 일과 답할 곳을 적는다.
아래 `<@BUILDER_ID>`와 `<@COORDINATOR_ID>`는 실제 Discord 사용자 ID로 바꿀 자리다.
사람에게 부탁할 때도 그 사람을 멘션한다.

```text
[조정 → 개발] <@BUILDER_ID> 변경 사항을 검토하고 이 글에 받음 답과 끝 시각을 알려 주세요.
```

## 받음 답과 결과 보내기

받음 답은 부탁한 상대를 멘션하고, 받을 일과 끝 시각을 바로 적는다.
원문에 답글로 연결하고 상대를 멘션하면 여러 부탁 중 어느 것에 답하는지도 분명해진다.

```text
[개발 → 조정] <@COORDINATOR_ID> 받았습니다. 검토 결과를 18:30까지 이 글에 답하겠습니다.
```

끝 시각은 `HH:MM까지` 또는 `내일 HH:MM까지`로 하나만 쓴다.
추적기는 설정된 `timezoneOffsetMinutes`를 사용한다.
결과도 부탁한 상대를 멘션하고 원문이나 받음 답에 답글로 잇는다.
약속 시각을 바꿀 때는 추적기가 다음 연결 답글을 결과 신호로 본다는 점을 고려해
원래 부탁을 결과와 함께 닫고 새 부탁으로 기한을 정한다.

## 멘션을 빠뜨렸을 때

[bot-mention-wake](bot-mention-wake.md)는 봇 사용자 멘션, 봇이 속한 역할 멘션,
봇에게 보낸 개인 메시지를 받아 깨움 파일을 만든다. 멘션 없는 이름 부르기는
이 장치의 감지 범위 밖이다. 별도 중계기가 설정된 인스턴스에서는 글 머리
`[보내는 이 → 받는 역할]`, 본문의 `역할에게`·`역할께`·`- 역할:`로도 깨울 수 있다.
중계기의 이름 감지에는 별도의 메시지 내용 접근 권한이 필요하다.

[agent-request-watch](agent-request-followup.md)는 설정된 역할 봇 사이의 부탁을
멘션 또는 위 역할 표기로 찾아 추적한다. 사람의 부탁은 이 추적기의 대상이 아니다.
받는 봇의 답에 부탁한 봇 멘션이나 원문·기록된 받음 답에 대한 답글 참조가 있어야
받음으로 인정한다(`requireMentionInReply`, 기본 `true`). 추적기는 호환성을 위해 둘 중
하나만 있어도 받을 수 있지만, 공통 메시지 규칙은 둘 다 요구한다. 답글 참조는 추적기의
연결 증거일 뿐 알림은 아니므로, 메시지 작성자는 답글에도 상대 멘션을 붙인다.
참조 없는 답이 여러 부탁에 걸리면 어느 부탁인지 확정할 수 없어 받음으로 인정하지 않는다.

상대 멘션과 유효한 답글 참조가 모두 없으면 받음 답을 쓰더라도 원래 부탁은 계속 열린다.
기본 10분 뒤 받는 역할을 다시 부르고 세션 상태를 읽으며, 30분 뒤 부탁한 역할에게 알린다.
받음 답에 끝 시각이 있으면 그 시각 이후 결과를 확인하고, 기본 20분 뒤 부탁한 역할에게 알린다.
`requireMentionInReply: false`는 인스턴스에서 명시적으로 허용할 때만 단일 부탁에 대한
멘션 없는 답을 인정하는 예외다. 공통 규칙의 기본값은 멘션 필수이므로 `true`를 유지한다.

끝 시각 없는 답은 받음 추적만 닫으며 일의 완료를 증명하지 않는다.
깨움 파일도 도착 증거다. 실제 답과 완료는 [깨움 완료 기준](wake-completion-contract.md)으로 확인한다.

## 사람 답변을 기다릴 때

이미 지시가 있고 되돌릴 수 있는 일은 다시 묻지 않는다. 먼저 그 채널 앞 글을 읽어 받은 지시를 확인하고 진행한다. 사람에게 물어야 한다면 멘션이나 답글 참조와 함께 “N분 안에 말씀 없으면 이렇게 진행하겠습니다”를 적는다. 바깥 발송·운영 변경·돈 등 실제 승인이 필요한 일은 침묵으로 승인받은 것으로 보지 않고 업무 요청 채널의 `[분류]` 양식으로 옮긴다. 주 감시는 업무 카드(`.agents/scripts/task-cards.mjs`)다. `waiting` 카드에 `wait_reason`과 다시 볼 시각 `recheck_at`(내보낸 장부의 `due_at`)을 반드시 적고, 사람 승인을 기다리면 요청 글 주소·번호 `request_ref`도 적는다.

[업무 장부 감시](../common/work-ledger.md#사람-기다림-감지)의 메신저 질문 추론은 대기 카드가 없을 때 한 번 깨워 카드를 남기게 하는 보조 안전망이다. 설정된 봇이 사람에게 질문한 뒤 기본 15분 동안 그 사람의 답이 없으면 질문한 역할을 한 번 깨운다. 감시기가 카드 존재를 조회하지는 않으므로 깨움을 받은 역할이 기존 카드를 먼저 확인한다. 카드가 없고 계속 승인을 기다려야 하면 대기 카드를 `waiting`으로 남긴다. 질문한 봇의 다른 주제 글이나 다른 봇에게 한 답은 대기를 닫지 않는다. 같은 채널의 그 사람 글, 질문을 참조한 답글과 보관된 쓰레드를 포함한 질문 쓰레드의 답을 확인하며 1:1 채널과 분할 글도 확인한다. 질문 문구·기다릴 시간·봇 사용자 ID와 역할 연결은 인스턴스 설정에 둔다. 질문마다 상태 파일로 한 번만 깨우며 메신저에 글을 보내지는 않는다. 에이전트 사이 부탁의 10분 재호출과 별도로 사람을 기다리다 멈춘 상태를 확인한다.

## 사실과 다음 행동

사람에게 보내는 글에서 구체 방법이나 근거 없는 노력·다짐·반성 표현을 쓰지 않는다. 사과나 다짐 대신 확인된 사실과 다음 행동 한 가지를 쓴다. 약속에는 무엇을 할지, 어떤 장치·파일·명령으로 할지, 업무 장부에 기록한 기한을 함께 적는다. 예: `검사가 빠져 있었다. scripts/message-guard.mjs를 연결하고 장부 기한 18:30까지 시험한다.`

일꾼을 띄웠거나 구동했다고 할 때는 실제 일꾼 폴더와 상태를 확인한다. 해소·병합·배포 등 진행 주장은 해당 폴더, 커밋 해시, PR 또는 배포 주소를 같은 문장에 적는다. 폴더만 만들거나 깨움 파일만 남긴 것은 구동 성공의 증거가 아니다.

공통 검사기 `scripts/lib/message-guard.mjs`의 `assertMessage(body, options)`는 차단 사유와 바꿔 쓸 꼴을 담아 오류를 던진다. `checkMessage`는 `{ok, issues}`를 돌려준다. `node scripts/message-guard.mjs 본문파일` 또는 표준 입력으로 검사하며 차단 시 종료 코드 1, 설정·입력 오류 시 2를 반환한다. 금지 패턴은 `scripts/lib/message-guard-patterns.json`에서 관리한다. 검사기는 문장 단위의 패턴 검사이므로 사실 여부와 약속의 모든 필수 요소를 이해하거나 보증하지 않는다. 작성자가 근거와 장부 기한을 직접 확인해야 한다.

`scripts/messenger/msg.mjs`의 `post`와 `scripts/notify.mjs`의 `send`는 전송 전에 검사한다. 별도 인스턴스의 Discord 도구도 본문 전송 직전에 `assertMessage(body)`를 호출해야 한다. 상대 경로는 프로세스 작업 디렉터리를 기준으로 확인하며, 필요하면 `assertMessage(body, { cwd: 작업기준경로, unitStatus: (dir, sentence) => 상태확인결과 })`로 기준과 동기식 유닛 확인 훅을 지정한다. 훅은 성공일 때만 `true`를 반환해야 한다. 훅을 생략하면 폴더의 `brief.md` 또는 `run.sh` 존재만 검사하며 유닛 구동 성공을 확인하지 않는다.
