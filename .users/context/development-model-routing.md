# 개발 모델 배정

이 문서는 Alpha ADK 루트 협업 절차의 모델 배정 기준입니다. 가능한 경우 먼저 계약과 결정론적 검사를 수행하고, 범위가 정해진 일을 안전하게 처리할 수 있는 가장 저렴한 역할을 사용합니다. 위험도 또는 해결되지 않은 근거 부족이 있을 때만 상위 역할로 올립니다. OpenCode는 사용하지 않습니다. HY3는 격리된 벤치마크에서만 평가할 수 있고 운영 라우팅에는 사용하지 않습니다. 벤치 통과만으로 이 금지가 자동 해제되지 않으며 별도 정책 결정이 필요합니다.

## 범용 계약 계층

정본 규칙은 Codex나 Claude의 모델명이 아니라 `조정자·탐색자·설계자·구현자·테스터·독립 리뷰어·중재자·번역자`의 능력과 증거를 정의합니다. 특정 CLI 플래그와 모델명은 어댑터에만 둡니다. 따라서 다른 도구도 같은 역할 능력, 계약 범위, 동일 수정본 해시, 서로 다른 역할·세션·실행 ID, 실패 시 차단 조건을 충족하면 이 하네스를 사용할 수 있습니다.

모델 호출 전에는 결정론적 검사를 먼저 수행하고, 필요한 능력과 위험 수준을 만족하는 가장 저렴한 어댑터를 선택합니다. 필수 독립 역할을 제공할 어댑터가 없으면 셀프 체크로 대체하지 않고 차단합니다.

범용 역할은 어댑터에서 명시적으로 대응시킵니다. 구현자는 Codex의 worker에 연결하고, 번역은 Claude Haiku 4.5 → Codex GPT-5.6 Luna(low) → Claude Sonnet 순서의 저비용 fallback chain을 사용합니다. 모든 CLI 호출은 공용 stdin 기반 호출 함수를 사용하므로 긴 프롬프트를 명령행 인자로 전달하지 않습니다.

## Codex 어댑터

기본 조정자와 최종 통합 책임자는 Codex의 `gpt-5.6-sol`(중간 추론 수준)입니다. 계약 해석, 통합 결정, 최종 정리와 최종 파일 변경은 이 역할이 맡습니다.

| 업무 | 모델과 추론 수준 | 실행 범위 |
|---|---|---|
| 범위가 정해진 탐색, 컨텍스트 지도화, 근거 수집 | Codex Terra, 낮음 | 읽기 전용 |
| 승인된 범위의 구현 | Codex Terra, 중간 | 작업 공간 쓰기 허용 |
| 범위가 정해진 설계 대안 분석 | Codex Terra, 높음 | 읽기 전용 |
| 집중 테스트와 검증 근거 수집 | Codex Terra, 중간 | 작업 공간 쓰기 허용 |
| 수정본의 독립 적대 리뷰 | 가능하면 구현자와 다른 모델·공급자, 필수 패널은 Codex Terra, 높음 | 읽기 전용 |
| 고위험 통합 또는 미해결 리뷰 지적의 중재 | Codex Sol, 높음 | 읽기 전용 |

## Claude 어댑터

Claude는 특정 날짜가 붙은 오래된 모델 ID를 이 계약에 고정하지 않습니다. 설치된 Claude 설정에서 현재 지원하는 별칭 또는 모델명을 사용합니다.

- 경량 역할: 설치 설정이 지원할 때 기계적 분류, 번역 배치, 범위가 정해진 탐색에 사용합니다.
- 일반 역할: 설치 설정이 선택하는 일반 분석 또는 구현에 사용합니다.
- 상위 역할: 설계, 안전에 중요한 판단, 또는 해결되지 않은 리뷰 근거에만 사용합니다.

Claude 역시 같은 실행의 구현자와 적대 리뷰어를 겸할 수 없습니다.

## 독립 적대 리뷰

구현자의 셀프 체크는 유용하지만 적대 리뷰가 아닙니다. 적대 리뷰는 반드시 필요하며 가능한 경우 구현자와 다른 모델 또는 공급자를 우선합니다. 이 선호는 다음 필수 독립성 조건을 절대 완화하지 않습니다.

- `session_id`
- `execution_id`

리뷰어는 이전 또는 불명확한 상태가 아니라, 변경할 수 없는 같은 수정본 해시를 읽기 전용으로 검토합니다. 모든 변경은 수정본이 바뀌지 않은 상태에서 Codex Terra와 Claude Sonnet의 서로 독립적인 깨끗한 리뷰가 필요합니다. 로컬 영수증의 세션·실행 ID는 `.agents/progress/review-evidence/`에 보존한 원본 CLI 실행 기록에서 다시 계산하며 호출자가 적은 문자열만으로 인정하지 않습니다. 미해결 지적이 있을 때만 Sol 중재자가 근거를 판정합니다.

모든 리뷰 근거에는 계약 또는 요구사항 ID, 수정본 해시, 구현자와 리뷰어의 세션·실행 ID, 그리고 테스트 기록이 포함되어야 합니다.

로컬 훅은 Codex가 훅에 노출하는 도구 경로를 위한 결정론적 안전장치입니다. 모호한 셸 쓰기는 승인 계약에 정확한 명령 패턴이 없으면 차단합니다. 프로세스와 모델의 암호학적 진위를 보장하는 경계는 서명된 격리 리뷰 실행이며, 일반 진행 JSON이나 로컬 훅 파일이 그 수준의 진위를 보장한다고 주장하지 않습니다.

## 비용 통제

스키마, 해시, 미러, 인덱스, 기록 확인은 LLM을 호출하지 않는 결정론적 검사입니다. 번역과 기계적 분류는 변경된 입력만 해시 캐시와 함께 경량 모델 배치로 처리합니다. Sol의 높은 추론 수준은 중재 또는 실제 고위험 업무에만 사용합니다.

## 빠른 적용 프로파일

1차 구조의 정본은 `packages/benchmark-contract/baselines/development-composition-profiles.json`입니다. 프로파일에는 오래 유지할 역할과 안전 조건만 두고, 현재 모델 바인딩은 분리합니다. 새 모델이 나오면 프로파일을 다시 설계하지 않고 해당 역할의 작은 실험과 바인딩 근거만 갱신합니다.

- `control`: 분리된 실행에서 모든 역할에 Sol을 사용합니다. 품질·비용 기준선이자 고위험 폴백입니다.
- `balanced`: Sol이 계획·통합을 맡고, 정확한 자동 검증기가 있는 제한 구현은 Luna가 수행합니다. 검증기가 없으면 Terra가 제한 구현을 맡고, Terra가 집중 테스트를 수행합니다. 지금 사용할 수 있는 opt-in 기본 프로파일입니다.
- `economy`: `balanced`의 안전 경계를 유지하면서 후속 근거가 생긴 Luna 기계 작업만 점진적으로 확장합니다.

Luna 구현은 범위가 제한되고 정확한 검증기가 있을 때만 허용합니다. 검증기가 없으면 Terra, 범위가 제한되지 않았거나 위험도가 높으면 Sol로 되돌아갑니다. 독립 리뷰는 작성자와 세션·실행 ID가 달라야 하며 가능하면 다른 모델 바인딩을 사용합니다. 1차 제공은 `balanced`를 사용할 수 있다는 뜻이며 전체 개발 조합의 비용 절감이 증명됐다는 뜻은 아닙니다.

## 벤치마크 후보와 승급 조건

Codex `gpt-5.6-sol`은 주 조정자이자 최종 통합자로 고정합니다. 벤치마크는 Sol을 대체하는 시험이 아니라, 제한된 하위 업무에 더 저렴한 모델·공급자·어댑터 조합을 사용할 수 있는지 검증하는 시험입니다. 서로 다른 공급자를 비교한 결과는 모델만의 인과 차이로 표현하지 않습니다.

- Codex Terra: 탐색, 구현, 테스트, 독립 리뷰 후보
- Codex Luna: 번역, 기계적 분류, 제한된 탐색 후보
- Azure `DeepSeek-V4-Flash`: 분석, 코드 생성, 구조화 출력 후보. 도구 호출 능력은 주장하지 않습니다.
- OpenRouter `tencent/hy3`: 분석, 코드 생성 후보. 도구 사용은 기능 탐색을 통과한 뒤에만 평가하며 실제 상위 공급자와 라우팅 방식을 고정합니다.
- Upstage 프라이빗 베타 `solar-open2`: 한국어 분석, 코드 생성, 문서 업무 후보. 키는 `UPSTAGE_KEY`로만 주입하고 저장소에 넣지 않습니다.

모델 능력 벤치는 고정된 과제를 모델에 실행하고 외부 채점기로 평가합니다. 에이전트 실행 벤치는 고정 모델로 실제 런타임과 장애 주입 도구를 실행합니다. 하네스 벤치는 모델에게 정답 상태를 추측시키지 않고 실제 훅과 검증기를 결정론적으로 실행합니다. 모든 재시도·fallback·시간초과·최종 실패를 품질과 비용 분모에 포함하고, 한국어 듀얼 컨텍스트와 Windows 네이티브 동작을 별도 검증하며, 동일 수정본에 대한 독립 적대 리뷰 2회가 깨끗해야 운영 라우팅으로 승급할 수 있습니다.

공통 모델 비교는 도구 없는 텍스트·JSON 과제로 제한합니다. 도구 호환성은 공급자별 별도 시험으로 기록하며 공통 점수와 합치지 않습니다. 후보 모델은 빈 임시 작업 폴더와 공개 입력만 볼 수 있고, 정답·채점기·manifest는 후보 프로세스와 설치 패키지 밖에 둡니다. 후보 출력 해시를 고정한 뒤에만 별도 채점 프로세스가 정답에 접근합니다. 각 시도는 새 세션을 사용하고 캐시 방식을 기록합니다.

개발 시험은 경로당 공개 과제 묶음 24개를 3회 실행하며 운영 판단에 쓰지 않습니다. 운영 승급 시험은 사전 검정력 분석 후 최소 80개 비공개 과제 묶음을 5회 실행합니다. Sol 대 다섯 후보를 하나의 Holm 보정군으로 묶고, 과제 단위 paired bootstrap 10,000회에서 품질 차이 하한이 -5%p 이상이며 비용 상한이 최소 15% 절감을 보여야 합니다. Sol 비교 작업자는 조정자와 분리된 최소 권한 세션으로 실행하고 조정 비용은 공통 부대비용으로 따로 기록합니다.

영수증에는 공급자, endpoint, API 버전, 원본 모델, 배포·라우팅 모델, 실제 상위 공급자, 어댑터 버전·해시, 요청 설정 해시, 사용량 변환 버전, 미지원 인자를 기록합니다. Authorization 헤더, API 키, 서명 URL과 자격증명 값은 기록·로그·해시 어디에도 넣지 않습니다. Windows는 Node 22 이상과 네이티브 PowerShell로 별도 통과하며 원격 모델 호출 성공이 Windows 하네스 통과를 대신하지 않습니다.

모든 벤치 저널은 레코드마다 HMAC 해시 체인을 만들고 분석 전에 다시 검증합니다. Windows에서는 네이티브 PowerShell 도우미가 HMAC 키를 CurrentUser DPAPI로 암호화해 보관하며 평문 키를 출력하거나 파일로 저장하지 않습니다. 코어 러너는 어느 플랫폼에서든 외부에서 키를 주입받는 구조이므로 DPAPI는 Windows 전용 어댑터일 뿐 다른 플랫폼의 의존성이 아닙니다. 키를 나중에 복구해 검증할 수 없는 실행은 교정 자료로만 취급하고 라우팅 판단에는 사용하지 않습니다.
