# Request-Contract Integrity Configuration

The canonical source is `.agents/context/request-contract.json`. This document is a human-readable mirror for downstream operators to understand the configuration intent.

## Activation

- Installation and enforcement are separate phases. Installing hooks and configuration does not authorize governed product work; until provisioning readiness passes, the delivery state is `REVIEW_ONLY`.
- `REQUEST_CONTRACT=on` and `node scripts/request-contract.cjs enable` are activation mechanisms only after all three credentials, public keys, executable allowlists, and the project readiness check are complete.
- **Current state — REVIEW_ONLY:** the installation is `installation_state: unprovisioned`; `preservation.required` alone no longer force-enables hooks. It provides local review policy only until signer, reviewer, runner, and allowlists are provisioned and the state is explicitly changed to `enforced`.
- After an unresolved unit or unaccepted quarantine is created, the marker cannot be deleted, `REQUEST_CONTRACT=off` cannot be set, and the `disable` command cannot be used to deactivate it midway.
- Before activation, the fixed public keys and credential IDs of distinct-authority signers, review runners, and quarantine runners, as well as the allowed reviewer, reviewer attestor, and runner attestor executable SHA-256 lists, must be supplied in the downstream configuration. Public-key fingerprints, as well as credential IDs, must all differ across the three roles; if values are missing or changed, governed mode fails closed. A general-purpose signer that signs arbitrary input must not be placed on the allowlist.
- Claude Code and Codex must each meet the minimum version fixed in the configuration. `PreToolUse`, `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PreCompact`, `PostCompact`, and `Stop` must each be registered exactly once with the exact adapter path, event arguments, repository root resolution, and matcher; missing, duplicate, or conflicting registrations fail closed. Command-line event arguments are for routing only; the native stdin event field must exist and have the same value. Codex `SessionStart|PreCompact|PostCompact` blocking uses the `continue:false`/`stopReason` format that the native dispatcher actually stops, and compact events do not emit the unsupported Claude-only `decision:block`/context envelope.

## Scope

- `product_roots: ["."]` observes the entire current Git repository. A gitlink records the actual files, index, and HEAD of the nested repository through recursive hashing rather than recording only a status string, so a byte change in an already-dirty file is detected as a new change. Git command failures and output-parsing failures are not converted into empty states, and manifest generation stops when an unreadable directory or unsupported file format is encountered. On Linux, backslashes are not converted into path separators, preserving `a\\b` and `a/b` as different files, and duplicate canonical keys are rejected rather than overwritten. If a configured root does not actually exist, it is explicitly marked as `missing`, so its later creation is also detected as drift.
- Only `.agents/harness`, `.agents/progress`, `.agents/reviews`, and `node_modules` at every depth are excluded by default. If a contract target or evidence points to an excluded path, binding is rejected.
- Git HEAD, the index, and recursive submodule state are recorded as separate occurrences from file contents. Evidence verifies the actual path and cannot read outside the product root through a symbolic link.
- Nested Git repositories are observed by each repository’s harness and recorded in the parent repository as a gitlink commit.

## Product-Preservation Contract

- The contract blocks execution only after request-contract provisioning and explicit `installation_state: enforced` activation. IDD and `verify-product-preservation` remain development procedures in an inactive repository and are not hook-level enforcement.
- With `preservation.required: true`, the contract must contain top-level `preservation.version`, `baseline_ref`, `intent`, `surfaces`, and `vendor_sources`. Surface dispositions are `preserve|extend|replace|remove|disable|redirect|migrate`; a destructive disposition is bound to an exact `authority_id` and an `expected_diff_digest` of the actual surface diff.
- The project adapter first derives the **exact complete surface set** from the immutable baseline, not a contract-author-selected subset. Every surface carries `kind`, `locator`, `baseline_paths/current_paths`, and distinct evidence IDs; omissions, additions, renames, and unreachable entries all require a disposition. UI, API, CLI, library, schema, job, package/deployment, operations, and handoff surfaces share this rule.
- Agents must not hand-author capability-probe JSON. **REQUIRED/PENDING:** an allowlisted project-adapter runner must execute the real entry and sign runner, command, exit, result, and subject bindings. Current JSON shape/digest/subject validation is not execution attestation and cannot alone yield `RELEASE_ELIGIBLE`.
- Conventional test/spec/vendor path detection is only a supplementary guard. Vendor provenance requires independent attestation of the origin repository identity, immutable commit/tree, and a digest computed from that origin tree. **PENDING:** immutable-ref syntax plus local subtree equality does not prove origin.
- The general floor is `minimum_clean_rounds: 2`. The preservation runtime requires four planning roles and four **new** integration roles with distinct execution/context/process and role-specific evidence views. It seals planning before the first implementation mutation, retains that seal across implementation-only changes, and requires fresh integration reviews for the current work revision.
- A `REVIEW_ONLY` checkpoint is local-commit-only by default. A remote review-branch push is publication and remains forbidden until an exact signed checkpoint operation is implemented and verified. With no classifier implemented yet, preservation runtime blocks every shell/publication event as `external_effect_gate_pending`; built-in release-command regexes are diagnostics only.

## Authority and Review

- Initial contracts and scope changes require an external user-presence signature containing a challenge, presentation digest, monotonic signature counter, one-time nonce, and exact target directive set. `authorize_contract` may be written exactly once and only to the initial contract. Pure additions are distinguished as `amend_scope_add`, corrections to existing non-terminal scope as `amend_scope_replace`, and removal states as `supersede|defer|abandon`. Non-terminal progress states such as `pending→active→done` and derived trace updates do not change semantic scope and therefore do not require separate user approval. Conversely, a target or acceptance criterion cannot be partially deleted from an existing directive; the previous directive must be closed with an exact tombstone and a reduced new directive added. Once disposed, a directive is rejected if its entire canonical directive changes in a later contract, and every tombstone is a canonical immutable record whose fields, description, authority, entity, and edges cannot be changed. A directive once disposed as `superseded|deferred|abandoned` cannot be revived as `active|done` or changed to another disposition. The core verifies fixed-key signatures and signed presence/non-exportable claims, but cannot independently prove that a key is actually non-exportable from hardware; therefore, that property and the physical/OS gesture are within the explicit provisioning trust boundary of the external signer.
- Every authority cross-links the exact `source_id`, original `source_digest`, and target directive included in the contract, and these values are included in the user-presence presentation digest. The source cited by an authority must be the `native_user` source determined directly by the adapter from the registered native `UserPromptSubmit` event, rather than the `origin` string sent by the caller. A prompt rejected and preserved in quarantine retains the same derived source. A subsequent scope authority must cite a later source that was not present in the previous contract. Reclassification of an existing source and modification of a tombstone’s description or authority record cannot be applied without a new scope authority, and the tombstone’s disposition state and complete entity/edge ID set cannot be changed even with new authority.
- Each source is decomposed into non-empty `obligation_atoms` that, when concatenated, are byte-for-byte identical to the original text. Atoms of directive, approval, and authority character map to one or more directives, and the union of source-level mappings and atom mappings must be exactly equal. The original atom text must be declared verbatim in one of the applicable directive’s statement, target description, or acceptance criterion. Each target, acceptance criterion, REQ, UC, UC-test, FE, FE-test, implementation, and evidence artifact also specifies the `obligation_atom_ids` it fulfills, and all seven trace edges for every atom must be actually connected; therefore, merely quoting the original text in a statement while dropping some obligations in later stages is rejected before semantic review.
- `scripts/request-contract-review-runner.cjs` is a platform-native launcher. On Linux, reviewer and bundle bytes are fixed by anonymous descriptors and executed in `bubblewrap` with separated PID, network, IPC, and UTS namespaces. On Windows, a digest-verified snapshot is sealed outside the repository and user home, reanalysis points are rejected, and inherited NTFS ACLs accessible only to the current user and SYSTEM are applied. The sandbox executable digest must also match the configured allowlist, and snapshot deletion failure fails closed. It then runs within the exact root policy of the Codex elevated sandbox, with the Node permission model reallowing only reviewer/bundle reads and scratch writes. Network, repository, and user-home access are blocked; WSL, Cygwin, MSYS2, Linux VMs, and Linux containers are not Windows dependencies. Review ingestion consumes one-time `runSandbox` evidence from the same process and fails if the semantic fields of the actual reviewer stdout differ from the ingested review. Public execution results expose only `verdict` and opaque `run_id`; `record_hash` and bundle binding values remain only in protected storage. The general operator CLI has no command for directly ingesting review JSON. The reviewer/runner attestors execute only executable snapshots fixed in the configuration and sign each digest and review-payload digest. The writer host’s PID, the reviewer’s PID, and platform-native process identities are also bound to the invocation, so the same process cannot be counted as an independent reviewer. The Windows writer identity queries the process start time anew at SessionStart and lock reclamation, and subsequent hooks reuse the value bound to the contract. Writable disk caches are not used. Linux uses `/proc` boot/start identities, while the Windows reviewer uses a per-execution unique identity created by the runner. Review time is fixed by runner evidence, and reviewer stderr and rejected fields/values are not reflected into external errors. Other operating systems require a platform runner for the same contract.
- The same `run_id`, challenge, reviewer context/process, and quarantine execution ID are permanently reserved as repository-wide claims and cannot be reused even after the original unit is compacted. `run_id` accepts only opaque IDs issued by the core, and findings accept only a fixed code set, preventing original text from leaking into public results.
- Immutable fields of the review invocation and the writer session/host process set are protected by the manifest digest bound by the global claim. The review bundle containing the original text and obligation atoms is written only to a private runtime path. POSIX enforces mode 0600; Windows verifies a non-symbolic regular file and seals it as an isolated snapshot. Only an opaque locator appears in stdout, and it is deleted after receipt acceptance or challenge expiration.
- The general completion floor is two consecutive Clean receipts bound to the current source/scope/work/config/binding. Preservation release additionally requires stage-bound planning×4 and integration×4 role receipts, trusted probe receipts, an exact baseline inventory, vendor-origin attestation, comparison/convergence receipts, and a project external-side-effect gate. Because the runtime does not yet prove all additions, a Clean preservation review is executable only as `REVIEW_ONLY`.

## Retention

- Original text and detailed records are private runtime state under `.agents/harness/`.
- Even before the initial binding, `Write|Edit` and Codex `apply_patch` may write control input only to the three files `pending/{contract-input,authority-presentation-input,resume-receipt-input}.json` of the current unit, so the actual hook path does not deadlock. Codex patches strictly interpret only a single `Add|Update File` section from the official native `tool_input.command`; multiple files, delete/move, absolute paths, and other targets are rejected. `Bash` is classified as a control command only for a single command invoking a trusted Node executable and the repository’s `scripts/request-contract.cjs`, or a review runner/attestor with a verified fixed digest. The unit, session, file path, and flags must match exactly; shell chaining, substitution, redirection, and unknown options fall back to ordinary mutation and are blocked while unbound. This control path does not create a product-change lease, so the initial `authority-challenge|bind` and the post-binding review runner are not blocked by their own lease.
- `PreCompact` runs the actual completion evaluation before the host reduces context. An incomplete contract blocks compaction, but this check does not consume an actual `Stop` attempt count or a terminal-incomplete transition. A contract that can be completed first generates a completion proof bound to the current workspace/source/scope/review chain and a one-time compaction approval bound to the client/session. `PostCompact` consumes that approval exactly once while revalidating the same proof and current workspace. Direct invocation, another client/session, reinvocation, absence of a prior proof, and drift during compaction all fail closed.
- Completion re-reporting such as `Stop` after a successful terminal state also revalidates the completion proof and current workspace. If a bypass change occurs after success, completion is blocked instead of reusing the previous success.
- If a successful existing session reports `Stop|SessionStart|PreCompact|PostCompact` again, the retained proof is revalidated against the current configuration and workspace. A separate new session is a new request lineage, so immediately before creation it verifies that every existing success proof is still current and binds the `genesis_workspace_digest` at that point to the new unit, leaving an explicit workspace handoff. Even if the new request subsequently changes the workspace, the previous session cannot re-report success; retention cleanup can confirm the previous terminal as historical completion through the verified handoff.
- After the retention period following successful termination, only the version, random receipt ID, state, start/end/compaction times, and source/change/review counts remain. Before deletion, a unit without handoff re-verifies twice the terminal’s completion proof, current config/workspace digest, source/scope/review chain, contract/binding digest, and consecutive Clean record hash. A handed-off unit verifies twice the exact terminal workspace digest bound to the subsequent genesis and the internal proof chain. A unit that only writes `success` to state, or changes files/configuration after success without a new lineage, cannot be compacted. After first recording the receipt in the durable journal, the entire unit is atomically renamed to a staging name, and only then are consumed quarantine and private staging deleted. Even if interrupted immediately after staging, the next retention run checks the receipt and proof and completes cleanup. Receipt IDs are not derived from internal unit/terminal digests; retries after compaction interruption use the same random ID prepared in the head. Atomic file replacement fsyncs the contents and parent directory, and transaction deletion also fsyncs the parent. Incomplete lineage is not compacted automatically; original text, contract, and signed resume state continue to be retained.
- Source append, contract binding, review ingestion, signed resume, and session binding, as well as lifecycle-state and head replacement, first write a preparation transaction and recover idempotently at the next lock acquisition if interrupted. The entire lifecycle state and the baseline’s own digest within it are bound to the unit head, so editing only the state file cannot erase occurrences or Stop counts. A unit/quarantine store that cannot be read is not treated as an empty list, preventing sticky governance from being silently released. The lock owner first completes work in a private candidate directory, then publishes it with a single rename, and rechecks directory identity and nonce immediately after publication and upon entry/release. Stale reclamation is serialized through a separate reaper so another reclaimer cannot acquire the new owner. When a new client/session attaches, the binding epoch and work revision both advance, invalidating the existing Clean result.
- The incomplete transition count increases only when the same failure fingerprint, including source/contract/config/workspace/binding, occurs consecutively. When actual progress changes the fingerprint, it starts as the first occurrence of a new failure episode; only the same unchanged failure reaching the configured count becomes terminal incomplete.
- `minimum_clean_rounds`, `stop_attempt_limit`, and `retention.success_hours` strictly validate finite integers and allowed ranges. Strings, fractions, and out-of-range values fail closed as configuration errors rather than being silently replaced with defaults.
- When adopting a quarantine source first captured in another session, the departure chain’s head/count/source ID set is also bound to the destination unit head. A mutable `consumed` marker in the departure file alone does not establish that it was consumed, and a retry after interruption records the same binding only once.
- `PreToolUse` blocks, before execution, mutating tools that lack not only genesis but also an active contract binding and classification for every source. `PostToolUse` compares the immediately preceding observed manifest after an allowed execution and collects modifications, reversions, and identical re-modifications as new occurrences respectively.
- A lease for which `PostToolUse` did not arrive because of another guard or a host permission rejection is closed with a cancellation record only by `Stop` from the same client/session after first observing the current workspace. If even one lease owned by another session is running, `Stop` is blocked without consuming an attempt, and review issuance is rejected until every lease is closed. Actual changes remain as occurrences, and even when there is no change, the owning session does not become permanently stuck in `mutation_in_flight`.
- If native `UserPromptSubmit` registration and envelope metadata conflict, or a valid prompt is blocked by a duplicate runtime binding, the string prompt is preserved in quarantine before returning a failure response. A successful Codex `Stop` uses empty stdout as normal continuation according to Codex’s official hook interpretation rules and outputs an explicit envelope only when blocking. The pre-change hooks for both Claude Code and Codex include `apply_patch`.

Even when a single operation involves multiple kinds of changes requiring authority, the core creates only one pending transaction from the sorted complete set of presentation digests. Each signature receipt consumes its own presentation exactly once, and the transaction closes only after the complete set has been consumed. If the set differs, the entire existing transaction is superseded and replaced with one new transaction.

## Honest Limitations

This layer is a collaboration-integrity defense that assumes normally operating local hooks and external signers. It is not an independent security boundary against an actor who disables the hook configuration itself, changes all local records and fixed keys together, an external signer signing false presence/non-exportable claims, or external side effects executed and fully restored between hook boundaries. Claude/Codex deterministic tests verify through each native adapter process boundary; dispatcher behavior of the installed host clients is a separate operational smoke-test scope.
