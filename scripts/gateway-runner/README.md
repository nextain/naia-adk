# Gateway runner

The six scripts in this directory are the versioned runner bundle; sync them together to an operator checkout and verify their hashes against the gate. The remote runner must be installed under a separately approved operational plan before using its new features.

`status-local.sh ENV RUN_ID env-names` reports only ABSENT, EMPTY or PRESENT for the six fixed Azure names, without requiring a saved run. It does not verify a key or region. The existing `recent` and `full-log` arguments are legacy aliases for the same status response; they do not retrieve logs.

For an approved deployment, `launch-local.sh ENV RUN_ID TAG DIGEST CURRENT REVISION backup ADDITIONS` accepts a canonical comma-separated list of source IDs, or `-` for no additions. The only mappings are `AZURE_TTS_KEY` to `azure-tts-key-v1` and `AZURE_TTS_REGION` to `azure-tts-region-v1`, in that order. Legacy invocations have no additions. Sources are root-owned 0600 regular files under root-owned 0700 `/opt/naia-gateway/env-sources`; provisioning them is a separate approved operation. The region must be an allowed Azure speech region. Values never belong in plans or commands. Backup snapshots the values for this run and deploy/verify/rollback use the snapshot and original backup. A missing or invalid source fails before the container changes.

Rollback recreates the previous container from its backup, but the runner's two forced `-e` options remain exceptions and it does not restore the database. A container replacement causes an interruption. Installation itself needs a separately approved plan and a confirmed installation receipt and hashes; stop on an interrupted or partial installation and investigate before using a new run ID.

Installation uses a separately approved `backup` launch with `-` additions. The staged pair is checked, backup runs from that exact pair, and the installed directory is switched as one version under an exclusive lock. Local operations take a shared lock and compare both installed files to the local bundle before use. Require both the backup and `INSTALL_OK` receipts, then run the separately approved `status-local.sh ENV RUN_ID installed-hashes` check; it reports `INSTALL_VERIFIED` only when both hashes match. A backup receipt alone is not installation confirmation.

The first switch preserves the former directory as `/opt/naia-gateway/deploy-runner.previous-RUN_ID`; later switches preserve the former symlink there. Keep the matching local and remote versions in sync and finish or explicitly account for runs started with the previous version before switching. If installation or its receipt is interrupted, stop: inspect the installed pair, retained previous version, run state and managed run-command resource under a separately approved recovery plan. Do not reuse the run ID or assume rollback occurred. Restoring the previous version also requires an approved operation and a matching local bundle.

A standalone `cleanup` runs the staged bundle without switching the installed runner. It may use its own run ID or precede a backup with the same run ID. The cleanup receipt does not imply installation. A remote installation `backup` requires a feature readiness record and its test and code gate receipts; the independent `installed-hashes` read requires an ops readiness record.
